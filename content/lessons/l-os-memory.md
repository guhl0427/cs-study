> 一句话定义：虚拟内存给每个进程一个「独占整台机器」的假象——CPU 发出的每个地址都经**页表**翻译成物理地址；隔离、超卖、懒加载，全靠这一层翻译。

## 概念讲解

### 虚拟 vs 物理：房卡与房间

类比：酒店前台给每位客人发一张「整层楼」的房卡，客人以为自己独占一层；实际住哪间房，由前台（**页表 + MMU 硬件**）实时翻译。程序眼里的一切地址都是**虚拟地址**，真正落在内存条哪里，只有翻译层知道。

| | 虚拟内存 | 物理内存 |
| ---- | ---- | ---- |
| 谁在用 | 每个进程一套，互不知晓 | 整台机器共享一份 |
| 大小谁定 | 进程的地址空间（64 位时代近乎无限） | 内存条的实际容量 |
| `ps` 里的名字 | VSZ / VIRT | RSS / RES |
| 何时真正分配 | 申请时只做登记 | 第一次写入时才给（懒加载） |

两个 8GB 内存的机器能同时跑几个「要 4GB」的程序，奥秘全在这一层翻译。翻译给三件事兜底：

- **隔离**：A 进程的虚拟地址 0x1000 与 B 进程的 0x1000 指向不同的物理页，A 写崩了也伤不到 B——进程隔离的物理基础，也是「一个进程崩溃不拖垮系统」的底气。
- **超卖**：物理内存不够也能跑——冷数据换到磁盘（**swap**），用到时再换回来。代价是换页慢几个数量级。
- **懒加载**：内存按「页」（通常 4KB）管理。malloc/new 只登记虚拟地址范围，**真正写入某一页时才分配物理内存**——那次写入触发一次**缺页中断（Page Fault）**，操作系统现场补货。

### 页表翻译：一次地址的旅行

```text
CPU 执行 mov [0x20001F40]，发出虚拟地址
        │
        ▼
  拆成两部分：页号 0x20001 ｜ 页内偏移 0xF40
        │
        ▼
  查页表（每个进程一张）：页号 0x20001 → 物理页框 0x7A3
  （页表不在的那一格 = 缺页中断：OS 补物理页，或从磁盘换入）
        │
        ▼
  物理地址 = 页框 0x7A3 拼上偏移 0xF40 → 内存条上的真实字节
  （TLB 缓存最近的翻译结果，命中则跳过查表，快上千倍）
```

要点三条：① 翻译是硬件做的，程序无感，但代价（缺页、TLB 失效）会体现在性能上；② 每进程一张页表，所以「两个进程打印出相同的地址」毫无冲突——翻译各自有各自的；③ 页是分配的最小单位，所以哪怕只申请 1 字节，物理内存也是按 4KB 领的。

### 地址空间布局：堆与栈各住哪（呼应 C 指针课）

每个进程的虚拟地址空间都是同一张地图：

```text
高地址 ┌──────────────────┐
       │ 命令行参数/环境变量 │
       │ ──────────────── │
       │  栈（向下长）↓     │ ← 函数调用帧、局部变量。
       │      ...         │    C 课里「局部变量住在栈上」住的就是这里，
       │      ...         │    printf("%p", &x) 打印的 0x7ffd… 即栈区
       │ （中间大片空洞）    │ ← 谁用谁登记：mmap 区、共享库映射在这
       │  堆（向上长）↑     │ ← malloc/new 的地盘；缺页时才领物理内存
       │ ──────────────── │
       │ 全局/静态/BSS      │ ← 程序一启动就在，不用申请
       │ ──────────────── │
低地址 │  代码段 .text      │ ← 机器指令本身（只读，写了就崩）
       └──────────────────┘
```

指针的值就是这里的虚拟地址：栈上的指针存堆对象的地址，堆里再存下一个地址，就串成了链表。栈向下长、堆向上长，中间的大空洞让两者都有余地——如果两者碰头，就是「内存耗尽」。CPython 的对象都在解释器的堆里，所以 `id(x)` 看到的地址是堆区；C 程序的局部变量地址才是真正的栈区。

### malloc 的背后一句话

`malloc(1GB)` 快得不可思议，因为它几乎什么都没干：只是在页表里登记「这段虚拟地址归你了」。等你的代码真的写入某一页，缺页中断触发，内核才把物理页塞给它。所以「申请成功」和「拿到内存」是两件事——这正是下面实验要亲手验证的。

### OOM 排错思路：谁杀了进程

内存排错的四个固定步骤：

1. **确认死因**：Linux 内存+swap 耗尽时，OOM killer 直接挑一个进程 SIGKILL——应用层没有异常栈、没有日志，进程「无声消失」。第一步永远是 `dmesg | grep -i oom` 找凶案记录（`Out of memory: Killed process …`）。
2. **分清谁在吃内存**：`free -h` 里 buff/cache 是页缓存（内核拿空闲内存做文件缓存，可回收，无害）；真正要盯的是各进程 RSS。
3. **看增长曲线**：RSS 单调涨不回落 → 泄漏嫌疑（用 tracemalloc、heap profile 定位）；有涨有跌 → 正常波峰；突然跳涨 → 某个请求/批量任务一次性装载了大数据。
4. **容器场景**：cgroup 限额触发 OOM 同样杀进程，退出码 137（128+9，SIGKILL）。`docker stats` 看实时用量，`docker inspect` 看 `OOMKilled: true`。

内存吃紧时系统整体变卡的机理也要懂：物理内存不足 → 大量页被换出到 swap → 每次访问都要从磁盘换回 → CPU 大量时间在等 IO。看起来像「CPU 慢」，实际是 swap 抖动（thrashing），加 CPU 没用，加内存或限流才有用。

## 代码示例

主线任务：双终端观察 1GB 申请的懒加载 → 看 RSS 爬坡 → 摸自己的地址空间地图 → 量缺页的时间成本。全程约 30 分钟。

### 第 0 步：认识观察工具

```bash
ps -o pid,rss,vsz,cmd -p <pid>    # RSS/VSZ 单位 KB；Linux/macOS 通用
# Windows 等价：Get-Process -Id <pid> | Select-Object Id, WS, PM
#   WS ≈ RSS（工作集），PM ≈ 私有内存提交量
```

### 实验 1：申请 1GB，物理内存分毫不动

```python
# demo_mem.py
import os, time

pid = os.getpid()
print("我的 PID:", pid, "——去另一个终端盯着我")
a = bytearray(1 << 30)                 # 「申请」1GB：此刻只登记虚拟地址
print("1GB 已申请，睡 15 秒……现在去查第一次 RSS")
time.sleep(15)
for i in range(0, len(a), 4096):       # 每 4KB 摸一个字节：逐页触发缺页中断
    a[i] = 1
print("数据已写入，再睡 15 秒……去查第二次 RSS")
time.sleep(15)
```

先跑 `python demo_mem.py`，再用打印出的 PID 在另一个终端观察两次：

```bash
ps -o pid,rss,vsz,cmd -p <pid>
```

预期输出（两次对比）：

```text
第一次：  RSS ≈ 15,000 KB    VSZ ≈ 1,120,000 KB   ← 申请了 1GB，实际没占
第二次：  RSS ≈ 1,050,000 KB VSZ ≈ 1,120,000 KB   ← 写过的页才真正拿到物理内存
```

输出说明了什么：**申请 ≠ 占用**。VSZ 在申请瞬间就涨了（登记额度），RSS 却几乎没动；逐页写入后 RSS 才爬上来。步长取 4096 正好对齐「页」的粒度——哪怕每页只写 1 个字节，也要为它领整页物理内存。Windows 上用 `Get-Process -Id <pid> | Select WS` 观察同样的两跳。

### 实验 2：逐块写入，亲眼看 RSS 爬台阶

```python
# demo_ramp.py
import time
a = bytearray(512 << 20)                   # 512MB，先只登记
for step in range(5):                      # 每轮写 100MB，写完停 8 秒
    start = step * (100 << 20)
    end = start + (100 << 20)
    for i in range(start, end, 4096):
        a[i] = 1
    print(f"已写入 {100 * (step + 1)}MB —— 快去另一个终端查 RSS")
    time.sleep(8)
```

预期输出：RSS 每 8 秒上一级台阶，约 +100MB/次，五级台阶到 ~500MB。输出说明了什么：缺页是按页逐次发生的，**RSS 曲线就是你写入进度的影子**。反过来看：一个服务的 RSS 曲线只涨不跌，就是内存泄漏的标准画像——这条曲线是后面排错练习的判据。

### 实验 3：摸一摸自己的地址空间地图（Linux/macOS）

```bash
cat /proc/self/maps | grep -E '\[heap\]|\[stack\]' 
# 典型输出：
# 55e2a0c2e000-55e2a0c50000 rw-p 00000000 08:01 1848110  [heap]
# 7ffd9a1a4000-7ffd9a1c5000 rw-p 00000000 08:01 1848111  [stack]
```

输出说明了什么：概念讲解那张布局图的实物版——heap 在低地址区，stack 在高地址区（0x7ffd 前缀），中间是空洞。对照 C 指针课：`&x` 打印出 0x7ffd… 的局部变量住栈区，`malloc` 返回的 0x55… 地址在堆区。Windows 上没有 /proc，等价视图是 VMMap 工具（Sysinternals）或调试器里的地址布局。

### 实验 4：量一量缺页中断的时间账

```python
# demo_fault_cost.py
import time
N = 1 << 30                     # 1GB
a = bytearray(N)
t0 = time.perf_counter()
for i in range(0, N, 4096):     # 第一遍：每页都触发缺页（向内核领货）
    a[i] = 1
t1 = time.perf_counter()
for i in range(0, N, 4096):     # 第二遍：页都在物理内存里，纯访问
    a[i] = 1
t2 = time.perf_counter()
print(f"第一遍 {t1 - t0:.3f}s（含缺页领货）, 第二遍 {t2 - t1:.3f}s（纯写入）")
```

预期输出（数字因机器而异，方向稳定）：

```text
第一遍 1.874s（含缺页领货）, 第二遍 0.612s（纯写入）
```

输出说明了什么：懒加载不是免费的——第一遍慢出的那部分就是十几万次缺页中断的处理成本。大内存程序「写入时明显卡一下」，根因常在这里；也再次解释了实验 1 中 RSS 为什么是写入时才涨。

## 常见坑

1. **坑 1：把 VSZ/VIRT 当真实内存占用**。现象：监控里进程 VIRT 30GB 就开始恐慌。原因：虚拟地址空间登记是「额度」不是「占用」。排查：一切以 RSS/RES 为准，看它的趋势而不是绝对值。
2. **坑 2：进程无声消失找不到日志**。现象：数据导入跑一半进程没了，应用日志一片空白。原因：OOM killer 在内核层 SIGKILL，应用来不及留遗言。排查：`dmesg | grep -i oom`，容器里再看 `OOMKilled` 标志。
3. **坑 3：malloc 成功就以为内存到位**。现象：大内存程序启动飞快、跑起来反而卡或崩。原因：overcommit 下 malloc 几乎总能成功，真实分配在首次写入；写入时可能触发换页甚至分配失败。排查：复现实验 4，量「首写」的成本；关键路径提前触碰内存（touch pages）。
4. **坑 4：把页缓存占用当内存泄漏**。现象：`free` 显示内存只剩一点，慌了。原因：buff/cache 是内核的文件缓存，内存空闲时自动占满、需要时自动让出。排查：看 `free -h` 的 available 列，再看各进程 RSS 谁在涨。
5. **坑 5：容器里进程被杀以为是代码 bug**。现象：容器化服务周期性退出，退出码 137。原因：cgroup 内存限额触发 OOM，与宿主机内存多少无关。排查：`docker inspect` 看 OOMKilled，`docker stats` 盯用量，核对限额与进程峰值。
6. **坑 6：系统卡顿就加 CPU**。现象：内存吃紧后整机变卡，扩容 CPU 无效。原因：swap 抖动——CPU 大量时间在等磁盘换页，us/sy 都不高、wa 很高。排查：vmstat 看 si/so 列（换入换出量）是否持续非零；药方是加内存、限流或修泄漏。

## 小练习

1. 跑实验 1，把两个时间点的 RSS/VSZ 记下来，用「登记 vs 占用」「缺页领货」各解释一遍；再把步长 4096 改成 1（每字节都写）重跑，观察第二遍 RSS 有没有意外变化并解释。
2. 用 `ps aux --sort=-rss | head`（Windows 用 tasklist 按内存排序）找出你机器上最吃内存的三个进程；再跑 `free -h`，判断这几个进程的 RSS 与 buff/cache 哪个大。
3. 思考题：8GB 物理内存的机器，为什么能同时跑加起来「要 20GB」的程序？写出这个把戏会在哪两个时刻露馅（提示：一个和 swap 有关，一个和 OOM killer 有关）。
4. **综合排查任务**：容器里的 Python 服务运行三天后被杀，退出码 137；内存监控显示 RSS 随运行天数线性上涨。写一份 6 行诊断：① 确认死因用什么命令；② RSS 线性上涨指向什么问题；③ 用什么工具定位泄漏点（Python 场景提 tracemalloc）；④ 临时止血方案；⑤ 根治方案；⑥ 如何在测试环境提前发现（复现实验 2 的曲线观察）。
