> 一句话定义：虚拟内存给每个进程一个「独占整台机器」的假象——CPU 发出的每个地址都经**页表**翻译成物理地址；隔离、超卖、懒加载，全靠这一层翻译。

## 概念讲解

两个 8GB 内存的机器，能同时跑好几个「要 4GB」的程序（32 位时代每个进程都以为独占 4GB）？因为程序拿到的是**虚拟地址**。类比：酒店前台给每位客人发「总统套房」房卡，客人以为独占一层楼；实际住哪间，由前台（**页表 + MMU**）实时翻译。每个进程一张页表，这一层翻译让三件事成立：

- **隔离**：A 进程的虚拟地址 0x1000 与 B 进程的 0x1000 指向不同物理页，互相写不坏对方——进程隔离的物理基础。
- **超卖**：物理内存不够也能跑，冷数据可以换到磁盘（**swap**），用到时再换回来。
- **懒加载**：内存按「页」（通常 4KB）管理。malloc 只登记虚拟地址，**真正写入时才分配物理内存**（触发一次**缺页中断 Page Fault**，操作系统补货）。申请 1GB 不写，几乎不占物理内存。

```text
      进程眼中的虚拟地址空间         实际去向（页表翻译）
高地址 ┌───────────────┐
       │  栈 ↓ 向下长   │ ──→ 局部变量、函数调用帧
       │       ...      │     （C 的指针存的，就是这里的地址）
       │  堆 ↑ 向上长   │ ──→ malloc/new 的地盘，缺页时才拿物理内存
       │ 全局/静态变量   │
低地址 │  代码段        │ ──→ 程序的机器指令
       └───────────────┘
```

`malloc`/`new` 的背后一句话：改一下页表登记（划一块虚拟地址范围），等你写入那一页才发生缺页中断、分配真实物理内存。

## 代码示例

亲手验证「申请不等于占用」——开两个终端，一个跑程序，一个盯内存：

```python
# demo_mem.py：申请 1GB，先不写，再每页写一个字节
import os, time
print("我的 PID:", os.getpid(), "——去另一个终端观察我")
a = bytearray(1 << 30)                # 「申请」1GB 虚拟内存
print("1GB 已申请，睡 15 秒……")
time.sleep(15)
a[::4096] = b"x" * (len(a) // 4096)   # 每页摸一下：逐页触发缺页中断
print("数据已写入，再睡 15 秒……")
time.sleep(15)
```

```bash
# 观察（Linux；macOS 类似，把 <pid> 换成上面打印的 PID）
ps -o pid,rss,vsz -p <pid>
# 第一次：RSS（真实物理占用）约 1~2 万 KB，VSZ 却已超过 1GB —— 懒加载！
# 第二次：RSS 涨到约 100 万 KB —— 写过的页才真正拿到物理内存
# Windows 等价：tasklist | findstr python，看「内存使用」列
```

再看进程的虚拟地址空间布局，堆栈位置一目了然：

## 常见坑

1. **坑 1：把 VSZ/VIRT 当真实内存占用**。虚拟地址空间登记 30GB 不代表吃了 30GB 物理内存。排查服务内存问题看 **RSS/RES**（常驻内存）并观察增长趋势。
2. **坑 2：进程「无声消失」找不到日志**。Linux 内存吃紧时 OOM killer 直接杀进程，不留异常栈。排查：`dmesg | grep -i oom` 找凶案记录。
3. **坑 3：malloc 成功就以为内存到位**。overcommit 下 malloc 几乎总能成功，真实分配发生在第一次写入；大内存程序要考虑写入时的延迟甚至分配失败。
4. **坑 4：把「内存吃满」直接当泄漏**。先分清是进程 RSS 在涨（泄漏嫌疑）还是系统页缓存占用（无害，可回收）。

## 小练习

1. 跑 demo_mem.py，在两个时间点用 ps 记录 RSS/VSZ，解释两次数字为什么差近百倍。
2. 用 `ps aux --sort=-rss | head`（Windows 用 tasklist）找出机器上最吃内存的三个进程。
3. 思考题：8GB 物理内存的机器，为什么能同时跑加起来「要 20GB」的程序？什么时候这个把戏会露馅？
