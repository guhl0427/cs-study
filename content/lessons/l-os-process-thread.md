> 一句话定义：进程是**操作系统分配资源的最小单位**（独立地址空间），线程是**调度的最小单位**（共享进程内存）——程序并发跑起来，靠的就是这两层结构。

## 概念讲解

### 类比：独栋别墅与合租室友

进程是一套**独立的房子**：门锁、家具（内存、文件句柄、网络端口）归这套房独享，别人进不来也改不了。线程是屋里**分头干活的室友**：共用同一套家具（堆、全局变量、打开的文件），但各带一本私人记事本（寄存器、自己的栈）。

操作系统给每个进程建一份档案——**PCB（进程控制块）**：存 PID、状态、寄存器快照、打开的文件清单；给线程的档案轻得多：一个栈加一份寄存器快照。档案轻重的差异，就是后面「创建成本、切换成本」差异的根源。

### 进程的一生：状态流转图

CPU 核心就几个，进程却几十上百个，「同时运行」是高速切换制造的错觉。进程一生在三种状态间流转：

```text
                新建完成，万事俱备
                       │
                       ▼
                 ┌───────────┐   被调度器选中    ┌───────────┐
                 │   就绪    │ ───────────────→ │   运行    │
                 │  Ready    │ ←─────────────── │  Running  │
                 └───────────┘ 时间片用完/被抢占 └───────────┘
                     ↑                           │
                     │       等待 IO/锁/网络响应    │
                     │ ┌───────────────────────── ↓
                     │ │        ┌───────────┐
                     │ │        │   阻塞    │
                     │ │        │ Blocked   │
                     │ │        └───────────┘
                     │ └── IO 完成/事件到达：先回「就绪」重新排队
                     │
                     │ 子进程已退出但父进程没收尸 ──→ 僵尸 Zombie（档案挂着等回收）
                     │ 父进程先死 ──→ 孤儿 Orphan（被 1 号进程收养，继续活）
```

三条关键直觉：

1. **阻塞时不占 CPU**——等服务端响应的线程不是在烧 CPU，是在门口排队。所以 `ps` 里 S（睡眠）远多于 R（运行），「大多数进程都在睡觉」才是系统常态。
2. 阻塞结束后只能回「就绪」重新排队，不能插队直接进「运行」。
3. 时间片用完的进程回「就绪」而不是「阻塞」——它没在等事件，只是在等下一个时间片。

### fork 与线程创建：复印房子 vs 添个工人

Unix 世界创建进程是一句 `fork()`——把当前进程**复印一份**：父子进程拿到几乎相同的内存、打开的文件，从同一行代码继续往下跑；`fork` 返回两次（子进程里得 0，父进程里得子 PID），想跑别的程序再调 `exec()` 把程序体换掉。类比：fork 是「复印一套房子连同家具」，exec 是「把屋里的图纸换成另一份」。

创建线程则只是**在同一屋里多叫一个工人**：不复印房子，只添一本记事本和一个工位（栈）。所以线程便宜、进程昂贵。细节差异：`os.fork()` 只在 Linux/macOS 存在，Windows 上 multiprocessing 用 spawn 模式从头启动一个新解释器（效果等价，成本更高），`threading` 则处处可用。

### 进程 vs 线程：完整对照表

| 维度 | 进程 | 线程 |
| ---- | ---- | ---- |
| 定位 | **资源分配的最小单位** | **CPU 调度的最小单位** |
| 地址空间 | 独立一套 | 共享所在进程的那一套 |
| 共享什么 | 几乎什么都不共享（要靠 IPC） | 共享堆、全局变量、fd；私有栈和寄存器 |
| 创建成本 | 高（建地址空间、登记资源） | 低（一个栈 + 寄存器快照） |
| 切换成本 | 高（换页表、TLB 失效、缓存污染） | 低（换寄存器和栈指针即可） |
| 崩溃影响 | 只死自己 | 一个崩，全进程陪葬 |
| 通信方式 | 管道、队列、socket（贵但安全） | 直接读写共享变量（快但易竞态） |
| 典型代表 | nginx worker、Chrome 标签页 | JVM/Gunicorn 里的请求处理线程 |

线程「私有 vs 共享」清单值得单独背下来：**私有**——栈、寄存器、程序计数器；**共享**——堆、全局变量、代码段、打开的文件（fd）。排错时先问一句：这个变量在共享区还是私有区？在共享区就提防竞态（下一课的主题），在私有区它就随线程生死。

### 为什么后端是「多进程部署 + 每进程多线程」

两层答案，各买各的好处：

- **进程层买隔离与多核**：nginx、gunicorn 都先起一个 master，再 fork 出多个 worker 进程。某个 worker 内存写坏了、句柄泄漏崩了，master 把它拉起来，其余 worker 照常服务；多核机器上每个 worker 占一个核，互不抢锁。
- **线程层买便宜并发**：同一 worker 内开多个线程处理请求，共享连接池、内存缓存——传个对象不需要序列化。线程崩了虽然会拖死所在进程，但「进程多」兜住了这个风险。
- 一句话：**进程买隔离，线程买共享；进程保命，线程干活。**

Python 的 GIL 是这条规律的注脚：同一进程内多线程同一时刻只有一个在执行 Python 字节码，所以 CPU 密集任务要用 multiprocessing 开进程，IO 密集任务线程仍然有效（等 IO 时会释放 GIL）。Chrome 给每个标签页独立进程、数据库一个连接一个线程，都是同一套取舍的变体。

### 僵尸与孤儿：成因与处理

- **僵尸进程**：子进程已经 `exit`，但父进程一直没调 `wait/waitpid`「收尸」，退出状态只能一直挂在进程表里。`ps` 里 STAT=Z、cmd 显示 `<defunct>`。它不占 CPU、不占内存，但占进程表项——堆积到上限后整个系统开不了新进程。
- 处理：① 找到父进程（僵尸的 PPID 列），修复它的回收逻辑（wait、SIGCHLD 处理）；② 短平快的手段是重启父进程，僵尸被 1 号进程收养后由它统一回收。**根因永远在父进程，不在僵尸本身。**
- **孤儿进程**：父进程先死，子进程被 1 号进程（init/systemd）收养，退出后由养父收尸——无害，很多守护进程故意「双 fork」制造孤儿让自己脱离终端。
- 观察工具：`ps -o pid,ppid,stat,cmd`（Windows 用任务管理器「详细信息」页或 PowerShell `Get-Process`）；`pstree` 一屏画出整棵进程树。

## 代码示例

主线任务：观察进程树 → 造孤儿 → 对比进程/线程的内存语义 → 复现僵尸 → 给真实服务画像。全程约 30 分钟。

### 第 0 步：观察你机器的进程树

```bash
ps -eo pid,ppid,stat,cmd | head -8
```

预期输出（节选，数字因机器而异）：

```text
    PID    PPID  STAT  CMD
      1       0  Ss    /sbin/init splash           ← 一切进程的祖先
    476       1  Ss    /usr/sbin/cron -f
   2210    1150  Ss    bash                        ← 你的 shell
   4120    2210  R+    ps -eo pid,ppid,stat,cmd    ← 正在跑的命令本身
```

输出说明了什么：PPID 列把所有进程串成一棵树，树根是 1 号进程；STAT 里 S 多 R 少——上一节「大多数进程都在阻塞」的直觉对上了。Windows 等价：任务管理器 → 详细信息自带进程树视图，或 PowerShell `Get-Process | Select-Object Id, ProcessName, StartTime`。

### 第 1 步：亲手造一个孤儿进程

```bash
bash -c 'sleep 600 & exit'        # 父 bash 启动后台 sleep 后立刻退出
ps -eo pid,ppid,stat,cmd | grep sleep
```

预期输出：

```text
  9201      1  S     sleep 600          ← PPID 已经变成 1：被 init 收养了！
```

输出说明了什么：父 bash 死后，sleep 没有跟着死，而是被 1 号进程收养、继续正常跑——这就是孤儿进程的现场，无害。第 0 步里它的 PPID 本来是那个 bash 的 PID；对比两次输出就能看到收养瞬间。

### 第 2 步：子进程改副本 vs 线程改本体

```python
# demo_pt.py：同一个变量，两种并发单元去改它
import multiprocessing as mp
import threading

counter = 0

def run_as_process():
    global counter
    counter = 100            # 改的是子进程自己那份「复印件」

def run_as_thread():
    global counter
    counter = 100            # 改的就是主进程里那个变量本体

if __name__ == "__main__":   # Windows 上 multiprocessing 必须有这行守卫
    p = mp.Process(target=run_as_process)
    p.start(); p.join()      # start 拉起子进程，join 等它跑完
    print("进程实验后 counter =", counter)

    t = threading.Thread(target=run_as_thread)
    t.start(); t.join()
    print("线程实验后 counter =", counter)
```

预期输出：

```text
进程实验后 counter = 0       ← 子进程改的是副本，改完整个世界对父进程不可见
线程实验后 counter = 100     ← 线程和主程序共用同一块内存，改完立刻可见
```

输出说明了什么：进程隔离是**物理级**的（独立地址空间），线程共享也是**物理级**的（同一块内存）。想让子进程的结果传回来，只能走 `mp.Queue`、`Pipe` 或 `Process` 的退出码——进程之间没有「共同的桌子」。另外注意 `if __name__ == "__main__"` 守卫：Windows 的 spawn 模式会重新 import 主模块，没有守卫会递归创建进程直接报错——这是 Windows 上 multiprocessing 的第一大坑。

### 第 3 步：复现僵尸进程（Linux/macOS 专属）

```python
# demo_zombie.py
import os, time

pid = os.fork()              # 复印自己：从此两个进程都在跑这一行之后的代码
if pid == 0:
    os._exit(7)              # 子进程立刻退出，退出码 7
else:
    print("子进程 PID:", pid, "——20 秒内去另一个终端看它的 STAT")
    time.sleep(20)
    # os.waitpid(pid, 0)     # ← 把注释打开，僵尸立刻被收尸
```

另一个终端（把 `<pid>` 换成上面打印的数字）：

```bash
ps -o pid,ppid,stat,cmd -p <pid>
#   PID   PPID  STAT  CMD
#  9341   9340  Z     [python] <defunct>     ← 20 秒里它一直是僵尸
```

输出说明了什么：子进程早就死了，档案却还挂着——因为父进程没 wait。打开 `waitpid` 那行再跑，STAT 里就没有 Z 了。生产上「重启父进程」能一键清僵尸，但根因永远在父进程缺一句回收代码。

### 第 4 步：给真实服务画像——数一数线程

```bash
ps -eo pid,nlwp,cmd --sort=-nlwp | head -5   # NLWP 列 = 该进程的线程总数
# 典型冠军是数据库、JVM、浏览器：几十到上百个线程
# ——「多进程部署 + 每进程多线程」不是教材口号，你机器上最忙的进程全长这样
# Windows 等价：tasklist 看「线程数」列，或 Process Explorer 的 Threads 页
```

## 常见坑

1. **坑 1：以为线程崩溃只死线程自己**。现象：某线程抛致命异常，整个服务一起退出。原因：线程没有独立地址空间，致命错误破坏的是全进程共享的内存。排查：崩溃日志分析的是「进程死因」，修复靠进程级兜底（supervisor 重拉 worker）。
2. **坑 2：以为子进程的修改能传回父进程**。现象：multiprocessing 子进程里改了全局变量，主进程读出来还是旧值。原因：独立地址空间，改的是复印件。修复：结果走 `mp.Queue`/`Pipe`/返回值。
3. **坑 3：僵尸进程堆积**。现象：`ps` 一排 `<defunct>`，时间长了系统开不了新进程。原因：父进程退出路径缺 wait。排查：`ps -eo pid,ppid,stat` 找僵尸的 PPID，修复父进程回收逻辑，应急重启父进程。
4. **坑 4：无节制多开进程**。现象：服务一开 500 个 worker 就 OOM。原因：每进程一套地址空间，内存占用直接 ×N。排查：算清「单进程 RSS × 进程数」再定 worker 数。
5. **坑 5：跨进程使用线程锁**。现象：子进程里的 `threading.Lock` 看起来完全不起作用。原因：每个进程有自己的一份锁副本，锁的从来不是同一扇门。修复：跨进程同步用 `mp.Lock`、`mp.Queue` 等进程级原语。
6. **坑 6：Windows 上 multiprocessing 忘写 `__main__` 守卫**。现象：一运行就无限报错、疯狂拉起进程。原因：spawn 模式重新 import 主模块，模块顶层又创建进程，递归爆炸。修复：创建进程的代码全部放进 `if __name__ == "__main__":`。

## 小练习

1. 跑第 0 步实验，找一个 STAT=S 的进程，根据 cmd 猜猜它在等什么事件；解释为什么 R 的进程这么少。
2. 把第 2 步实验改造成：子进程往 `mp.Queue` 里放 `100`，父进程 `q.get()` 收到——亲手体会「进程之间要靠邮局，线程之间共用桌子」。
3. 完整复现第 3 步的僵尸，先后验证两件事：打开 `waitpid` 后 STAT 恢复正常；不打开注释直接杀掉父进程，僵尸也会消失（想想为什么）。
4. **综合排查任务**：线上 Python 服务同时出现三种症状——① RSS 随运行天数缓慢上涨；② `ps` 里偶现 `<defunct>`；③ 偶尔一个线程崩导致整个 worker 退出。写出每个症状分别指向进程模型的哪个环节、用什么命令验证、修复方向是什么（提示：泄漏看 RSS 趋势，僵尸看父进程回收路径，崩溃看多进程隔离是否到位）。
