> 一句话定义：TCP 和 UDP 是传输层的两种发货方式——TCP 先签合同（握手）、确认签收（应答）、丢了重发；UDP 只管把包扔出去，快但不可靠。

## 概念讲解

应用层数据要跨过整个互联网才能到达对方，路上可能丢、可能乱序、可能重复。传输层就是解决「怎么送」的：

| 维度 | TCP | UDP |
| ---- | ---- | ---- |
| 建立连接 | 三次握手 | 无连接，直接发 |
| 可靠性 | 确认 + 重传 + 排序 | 不保证 |
| 速度 | 慢一些（要做保障工作） | 快 |
| 适用 | 网页、文件、API | 直播、游戏、DNS 查询 |

**三次握手**（TCP 建立连接）白话版：

```
客户端：能听到吗？（SYN）
服务端：能，你能听到我吗？（SYN+ACK）
客户端：能！（ACK）—— 开始传数据
```

三次而不是两次：**双方都要确认「自己说话对方听得见」**。第二次握手只能证明服务端的下行通了，还需要第三次让服务端确认客户端的下行也通。

**为什么 DNS 用 UDP？** 一次查询就一来一回，为它做三次握手 + 确认重传，成本远超收益；丢了大不了重问。这体现传输层选型的核心逻辑：**可靠性是花钱买的，按业务需要购买**。直播宁可丢两帧也不能停顿重传，所以选 UDP；网页要一字不差，所以选 TCP。

## 代码示例

```bash
# 观察 TCP 三次握手：新建连接的前几个包就是 SYN → SYN+ACK → ACK
curl -sv https://example.com -o /dev/null 2>&1 | head -5

# 观察 UDP：DNS 查询（53 端口，UDP）
nslookup qq.com

# 测一个端口的 TCP 连通性（传输层健康检查）
curl -sv telnet://smtp.qq.com:587 -o /dev/null 2>&1 | head -3
```

想做更直观的观察，可以开 Wireshark 抓一次 `curl https://example.com`，在过滤器输入 `tcp.handshake` 就能看到三次握手三条报文一字排开。

## 常见坑

1. **坑 1：以为「UDP = 一定会丢」**。UDP 只是**不承诺**可靠，局域网内丢包率可能极低。正确理解：UDP 把可靠性责任交给了应用自己（游戏一般自己补，视频自己忍）。
2. **坑 2：面试背了握手却说不出「为什么是三次」**。核心：让双方都确认双向链路可用。二次的问题在服务端无法确认自己下行是否被收到。
3. **坑 3：把端口和进程搞混**。端口是传输层交给应用层的「门牌号」（0–65535），一台机器 IP 只有一个，靠端口区分哪个程序收货。

## 小练习

1. 用 Wireshark（或浏览器 Network 的 Timing 面板）找到一次 HTTPS 请求里 TLS 之前的 TCP 握手耗时。
2. 解释为什么视频会议选 UDP：如果换成 TCP，卡顿时会发生什么？
3. 思考题：HTTP/3 直接跑在 UDP（QUIC 协议）上，它自己实现了哪些 TCP 才有的能力？
