> 一句话定义：TCP 和 UDP 是传输层的两种发货方式——TCP 先签合同（握手）、逐件签收（确认）、丢了重发，可靠但慢；UDP 把包裹直接扔出去，快但不管到没到。

## 概念讲解

![TCP 三次握手与四次挥手](fig:net-tcp-udp)

### 传输层到底解决什么

应用层数据要跨过整个互联网才能到达对方。路上会发生什么？**会丢**（路由器缓冲区满了直接丢弃）、**会乱**（不同包走了不同路线，后发的先到）、**会重**（网络抖动导致对方重复收到同一份）。IP 层只管「把包往对面送」，一概不承诺以上任何事。

传输层就是在这层不可靠的地基上，根据业务需要盖不同的房子：

- **TCP**：造一套「签收体系」——每个包编号、对方逐个确认、没确认的超时重发、到了按序号排好再交给应用。结果：数据一字不差、顺序不变。
- **UDP**：什么都不做，IP 包外面套个薄头就发。结果：快、开销小，丢没丢全看运气。

### 端口：传输层的门牌号

一台服务器的 IP 只有一个，但上面同时跑着网站、数据库、邮件……**端口（port，0–65535）就是传输层用来区分「包裹送给哪个程序」的门牌号**。客户端每次发起连接会随机领一个高位端口当「回执地址」，服务端则守在知名端口等你：

| 端口 | 服务 | 协议 |
| ---- | ---- | ---- |
| 22 | SSH 远程登录 | TCP |
| 53 | DNS 域名解析 | UDP（区域传输用 TCP） |
| 80 | HTTP | TCP |
| 443 | HTTPS | TCP（HTTP/3 用 UDP） |
| 3306 | MySQL | TCP |
| 6379 | Redis | TCP |

「IP + 端口」合起来才完整定位一次通信的两个端点。以后看到 `Connection refused`（门牌上没程序在听）和 `Connection timed out`（包裹根本没送到门口），就是端口层面的两种典型回应。

### TCP 三次握手：白话版与报文图

TCP 说话前要先「对上暗号」。三次握手用三个报文建立连接：

```text
 客户端                        服务端
    │ ── SYN：能听到吗？──────→ │     请求开门（seq=x）
    │ ←─ SYN+ACK：能，你呢？── │     开门+回执（seq=y, ack=x+1）
    │ ── ACK：能！───────────→ │     最终回执（ack=y+1）
    │ ══════ 连接建立，开始传数据 ══════
```

白话版：客户端问「能听到吗」→ 服务端答「能，那你听得到我吗」→ 客户端答「能」。**为什么必须是三次，两次不行？** 因为双方都要确认「**双向**都通」：

- 前两次只让客户端确认了「我发得出去、也收得回来」；
- 服务端此时只知道「有人发来了」，还不知道**自己的话能不能被对方听到**；
- 第三个 ACK 补上这一环，服务端才敢开工。

少这第三步还有个副作用：网络上会漂着「迟到多年的重复连接请求」，若两次握手就开门，服务端会为一个早已作废的请求白白开门等数据——第三次握手让客户端有机会说「那不是我要的」。同理，断开连接是**四次挥手**（两边各自说「我说完了」、各自被确认），比握手多一轮，因为断开是双向独立的，一句带过即可。

### 可靠性的实现：确认 + 重传 + 排序

握手只是开门。TCP 的「可靠」靠三件套维持整个会话：

1. **确认（ACK）**：每收到一段数据，接收方都回报「我收到第几号了」；
2. **重传**：发送方在计时器内没等到确认，就重发那段数据——丢了也不丢事实；
3. **排序**：每个字节都有序号，到达顺序乱了就按序号重排，交给应用时一定和发送时一模一样。

这些保障不是免费的：每一次确认都占带宽，每一次重传都意味着**等待**。这就是 TCP「可靠但慢」的账单明细。

### UDP 的裸奔哲学：把选择权还给应用

UDP 把 TCP 三件套全扔了：不握手、不确认、不排序——发出去就完事。听起来不可理喻，但对某些业务，「完整」恰恰是伪需求：

- **直播**：丢了两帧画面，观众几乎无感；若用 TCP，丢一帧就停下来等重传，画面直接卡死——**宁可丢，不可停**。
- **游戏对战**：位置包 100ms 后才到就已经作废了，重发一个旧的毫无意义。
- **DNS 查询**（下一课主角）：一来一回就完事，为一次查询做三次握手 + 确认重传，成本远超收益；丢了大不了重问一次。

注意：UDP 不是「一定丢包」，而是**不承诺**可靠。局域网里 UDP 丢包率可能极低；需要部分可靠性的应用（如实时音视频）还可以在应用层自己做「选择性重传」——把可靠性当成可按需购买的套餐。

### 选型对照表：可靠性是花钱买的

| 业务 | 选型 | 理由 |
| ---- | ---- | ---- |
| 网页、API | TCP | 一个字节都不能错 |
| 文件传输 | TCP | 必须完整 |
| 数据库连接 | TCP | 事务不能丢语句 |
| 直播、视频会议 | UDP | 宁可丢帧，不能停顿 |
| 实时游戏 | UDP | 旧数据重发毫无意义 |
| DNS 查询 | UDP | 一来一回，重问比重传便宜 |

判断标准一句话：**丢了会出事的选 TCP，过期作废的选 UDP**。补充一句前沿：HTTP/3 把 HTTP 搬到了基于 UDP 的 **QUIC** 协议上——它在应用层重新实现了可靠性，换来更快的握手与移动网络切换不断流，相当于「拿着 UDP 的速度指标，把 TCP 的可靠性自己重写了一遍」。

## 代码示例

主线任务：亲手测量「TCP + TLS 握手」的成本，验证连接复用，并从操作系统视角看端口。全程约 20 分钟。

### 第 1 步：看一次握手的直接证据

```bash
curl -sv https://github.com -o /dev/null
```

预期输出（节选）：

```text
* Trying 140.82.x.x:443...
* Connected to github.com (140.82.x.x) port 443
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
* SSL connection using TLSv1.3 / ...
```

输出说明了什么：`Connected` 出现，意味着 SYN → SYN+ACK → ACK 三次握手在毫秒间完成（你看不到三个包，只看到结果）；随后 TLS 又握了一轮。**TCP 握手 ≈ 1 个往返（RTT），TLS 1.3 握手再加 1 个往返**——这就是「建连成本」的物理构成。

### 第 2 步：分段计时——握手到底花了几毫秒

```bash
curl -s -o /dev/null \
  -w "DNS解析:%{time_namelookup}s TCP握手:%{time_connect}s TLS握手:%{time_appconnect}s 首字节:%{time_starttransfer}s 总计:%{time_total}s\n" \
  https://github.com
```

预期输出（数值随网络浮动，比例关系才是重点）：

```text
DNS解析:0.012s TCP握手:0.048s TLS握手:0.096s 首字节:0.130s 总计:0.150s
```

逐段判读：

- `TCP握手 - DNS解析` ≈ 0.036s：一个 RTT 花在三次握手上；
- `TLS握手 - TCP握手` ≈ 0.048s：又一个 RTT 花在 TLS 上；
- `首字节 - TLS握手` ≈ 0.034s：服务器真正「想」并吐出响应的时间（后端处理）；
- 结论：**还没开始传任何业务数据，已经花了约 0.1 秒**——握手是纯开销，这就是为什么全行业拼命做连接复用。

### 第 3 步：验证连接复用——第二次为什么几乎免费

```bash
curl -s -o /dev/null -o /dev/null \
  -w "第1次 TCP:%{time_connect}s TLS:%{time_appconnect}s 总:%{time_total}s\n" \
  -w "第2次 TCP:%{time_connect}s TLS:%{time_appconnect}s 总:%{time_total}s\n" \
  https://github.com/ https://github.com/about
```

预期输出（示意）：

```text
第1次 TCP:0.048s TLS:0.096s 总:0.210s
第2次 TCP:0.000s TLS:0.000s 总:0.070s
```

输出说明了什么：第二条 URL 的握手时间全是 0——curl 在同一进程里**复用了第一条 URL 建立的 TCP 连接**，第二次请求直接在旧通道上跑。这正是浏览器打开页面后「后续请求快得多」的原因：**TCP 连接是建一次、用多次的资产**（HTTP 的 keep-alive 机制）。

### 第 4 步：从操作系统视角看端口

```bash
netstat -ano | findstr :443     # Windows；macOS/Linux 用 ss -tnp | grep 443
```

预期输出（节选）：

```text
TCP    192.168.1.103:53122    140.82.121.4:443    ESTABLISHED     15840
TCP    0.0.0.0:8080           0.0.0.0:0           LISTENING       12020
```

逐行判读：`ESTABLISHED` 行表示一条已建立的 TCP 连接——左边是你的「临时端口 53122」（客户端回执地址），右边是对方的 443；`LISTENING` 行表示本机 8080 端口有程序**正在守门**。这一命令是排查「端口被占用」的第一现场：末列是进程 PID，Windows 下用 `tasklist /fi "PID eq 12020"` 查出是谁。

### 第 5 步：亲眼看 UDP 的身影（可选：Wireshark）

nslookup 走的是 UDP 53 端口——装上 Wireshark，选中你的网卡开始捕获，然后：

```bash
nslookup qq.com
```

在 Wireshark 过滤器输入 `udp.port == 53`：能看到一来一回的两条 DNS 包，**没有握手、没有确认**——UDP 的极简一眼可见。再看 `tcp.port == 443 && tcp.flags.syn == 1`：SYN 与 SYN,ACK 成对出现，三次握手的三条报文一字排开。两种协议的「性格差异」从此不再是想象。

### 第 6 步：浏览器侧的握手观察（DevTools Timing）

打开任一网站 → F12 → Network → 勾选 Disable cache → 刷新 → 点开第一条主文档请求 → **Timing** 标签：

预期看到：`Initial connection`（TCP 握手）与 `SSL`（TLS 握手）两段各占几十毫秒；而同页后续请求的这两段是 0（复用连接）。

输出说明了什么：首页首个请求天然要付「DNS + TCP + TLS」三笔建连税，页面内后续请求几乎免税——**性能优化常说的「减少请求数」「域名收敛」，省的正是这些握手**。

## 常见坑

1. **坑 1：以为「UDP = 一定丢包」**。现象：推荐 UDP 时被质疑「数据会全丢」。原因：UDP 只是不承诺可靠，局域网内丢包率可能极低。正确理解：可靠性交由应用按需自建（游戏自己做补偿，视频容忍丢帧）。
2. **坑 2：背了「三次握手」却说不出为什么不是两次**。现象：面试背诵流利，追问哑火。原因：没抓住核心——**双方都要确认双向可达**，前两次只让客户端确认了双向，第三次才让服务端确认「我说的话对方听得见」。对策：默写报文图时同步写出每一步「谁确认了什么」。
3. **坑 3：把端口和进程、IP 和端口搞混**。现象：以为「一台服务器一个端口」或「端口就是程序」。正确理解：端口是 0–65535 的门牌号，一个端口同一时刻只能被一个进程监听；IP 定位机器、端口定位机器上的程序。
4. **坑 4：启动服务报「端口被占用」只会重启电脑**。现象：起本地服务报 `Address already in use`。原因：80/443/8080 这类热门端口常被别的进程占着。排查：`netstat -ano | findstr :8080` 找 PID → `tasklist /fi "PID eq xxx"` 看是谁 → 结束它或换端口。
5. **坑 5：页面慢就怪带宽**。现象：首屏慢，先怀疑网速。原因：建连阶段（DNS+TCP+TLS）的开销与带宽无关，与**往返延迟（RTT）和握手次数**有关。排查：用第 2 步的分段计时看握手占比；占比高时优化方向是连接复用/就近接入，不是加带宽。
6. **坑 6：以为握手耗时能靠前端代码优化掉**。现象：前端疯狂优化 JS，首字节还是慢。原因：握手发生在传输层/网络层，JS 优化无济于事。对策：走浏览器 Timing 判断——握手慢查网络与部署位置，Waiting 慢才查后端。

## 小练习

1. 用第 2 步的分段计时命令对三个网站各跑三次，记录 DNS/TCP/TLS 三段耗时，回答：哪家握手开销最大？它和「离服务器的物理距离」是什么关系？
2. 用 `netstat -ano` 找出你机器上所有 `ESTABLISHED` 到 443 端口的连接，并用 `tasklist` 查出是哪个进程建的——你会看到浏览器一个进程维护着多条连接。
3. 用 Wireshark（或 DevTools Timing）分别截图记录「UDP 的一来一回」与「TCP 的三条握手报文」，各用一句话说明两者性格差异。
4. **综合排查任务**：某接口首字节要 1.5 秒。先用分段计时把总时间拆成「建连（DNS+TCP+TLS）」与「首字节」两段：若建连占大头，下一步查什么？若首字节占大头，又查什么？写出两种情形各自的排查命令。
