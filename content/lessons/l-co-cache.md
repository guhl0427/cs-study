> 一句话定义：快的存储贵、慢的存储便宜，所以计算机把它们叠成金字塔，再用缓存和局部性原理，让程序「感觉上」住在一套又快又大的存储里。

## 概念讲解

### 存储金字塔：相邻两层差 10~1000 倍

```text
          ┌─────────┐
          │ 寄存器   │   ~0.3 ns / 几十字节       手里正在算的数
        ┌─┴─────────┴─┐
        │ L1 缓存      │   ~1 ns / 几十 KB         桌上摊开的笔记
      ┌─┴─────────────┴─┐
      │ L2/L3 缓存       │   ~4~15 ns / 百 KB~几十 MB  身旁书架
    ┌─┴─────────────────┴─┐
    │ 内存 DRAM            │   ~100 ns / GB 级         家里储藏室
  ┌─┴─────────────────────┴─┐
  │ SSD                      │   ~0.1 ms / TB 级         楼下超市
┌─┴─────────────────────────┴─┐
│ 机械磁盘                     │   ~10 ms / TB 级还便宜     郊外仓库
└─────────────────────────────┘
```

| 层 | 延迟（约） | 容量（约） | 类比 | 人类尺度（CPU 1 次运算 = 1 秒） |
| ---- | ---- | ---- | ---- | ---- |
| 寄存器 | 0.3 ns | 十几 × 几十字节 | 手里的笔 | 1 秒 |
| L1 | 1 ns | 32~64 KB | 桌上笔记 | 3 秒 |
| L2 | 4 ns | 256 KB~1 MB | 书架 | 13 秒 |
| L3 | 15 ns | 几~几十 MB | 楼道储物柜 | 50 秒 |
| 内存 | 100 ns | GB 级 | 储藏室 | 5 分钟 |
| SSD | 100 μs | TB 级 | 超市 | 1~2 天 |
| HDD | 10 ms | TB 级 | 仓库 | 2~4 个月 |

类比：你在书桌前写作业，伸手拿笔瞬间完成；起身去书架取一本书的时间，够你伸手拿桌上东西几十次；下楼去超市的时间，够你从书架取书几千次。所以「把常用的搬到桌上」就是缓存的全部思想——**每贵一分钱买一倍速度，就用一层缓存兜底**。

### 局部性：缓存生效的全部前提

缓存赌的是程序访问内存的两条经验规律：

- **时间局部性**：刚访问过的数据，很快会再访问——循环变量、反复用的计数器、刚加载过的函数代码马上又被调用。
- **空间局部性**：访问了某地址，旁边的地址很快也会被访问——挨个遍历数组、顺序读文件、执行下一条指令。

程序一旦违背两条（大范围随机跳着访问），缓存就无能为力：数据搬上来还没用就被换走。**写高性能代码的第一件事，就是检查访问模式是不是「成片」的。**

### 缓存行 64 字节：搬运的最小单位

缓存与内存之间**按 64 字节整块搬运**：哪怕只读 1 个字节，硬件也把整个 64 字节搬上来。这对程序员是好消息——只要按地址连续访问，「邻居」全部免费搭车：

```text
内存（按地址连成一条）：
… [a[0] a[1] a[2] … a[15]] [a[16] … a[31]] …
    └──────── 64 字节 ────────┘
读 a[0]：整块上车 → a[1]~a[15]（int 4B × 16 个）已经在缓存里，全命中 ~1ns
```

代价表：命中（数据已在缓存）约 1ns；未命中（要下一层取）约 100ns——**一次未命中够 ALU 干几百条指令**。程序快慢的分水岭，往往就在命中率上。

### 按行 vs 按列：布局决定命运

二维数组在内存里是**按行连成一条**的：

```text
a[1000][1000] 的内存：[a[0][0] … a[0][999]] [a[1][0] …] …
按行遍历：地址每次 +4 字节   → 一个缓存行喂 16 次访问，几乎全命中
按列遍历：地址每次 +4000 字节 → 一个缓存行喂 1 次就丢，几乎全未命中
```

两种写法访问次数完全相同、复杂度都是 O(n²)，速度却差一个数量级——这就是那道经典面试题的全部原理，下面亲手测。

### 对程序员的实际意义

- **数据布局的收益常常大于算法微调**：优先用连续内存（数组优于指针乱跳的链表，即使都是 O(n)）；把一起用的数据放一起。
- **C 结构体对齐一句**：编译器会往字段间塞填充字节保证对齐访问，字段排序影响 sizeof——把大数据字段排一起能省内存，本质也是空间局部性的账。
- **慢速层同理**：数据库 B+ 树把节点做成「一个磁盘页」大小，一次 I/O 搬回一整页键值，树矮、I/O 少——缓存行思想从纳秒层平移到毫秒层。
- **预取思想**：CPU 硬件检测到连续访问会提前搬下一块；数据库的预读、日志的顺序追加写，都是在「猜你下一步要什么，提前搬进快的那层」。

## 代码示例

主线任务：行/列计时 → 换 array 复测放大效应 → 顺序 vs 乱序 → stride 找拐点。全程约 25 分钟。所有「典型输出」因机器而异，**方向恒定、倍数看你自己机器**。

### 实验 1：按行 vs 按列（Python 列表版）

```python
# demo_grid.py
import time

N = 1024
grid = [[j for j in range(N)] for _ in range(N)]   # 1024×1024 二维列表

t0 = time.perf_counter()
total = 0
for row in grid:            # 按行：顺着内存方向挨个走
    for v in row:
        total += v
t_row = time.perf_counter() - t0

t0 = time.perf_counter()
total = 0
for j in range(N):          # 按列：每步跳一整行 1024 个元素
    for i in range(N):
        total += grid[i][j]
t_col = time.perf_counter() - t0

print(f"按行 {t_row:.3f}s, 按列 {t_col:.3f}s")
```

预期输出（典型值）：

```text
按行 0.190s, 按列 0.680s
```

输出说明了什么：访问次数完全相同，速度差 3 倍左右——纯布局差异。Python 的列表存的是指针、对象又散落在堆上，缓存效应打了折扣；同样的实验换成 C 的连续数组，差距能拉到 5~10 倍。但方向一致：**访问顺序决定缓存命中率**。

### 实验 2：array 模块版——真正的连续内存

```python
# demo_array.py
import time, array

N = 1024
flat = array.array("l", range(N * N))      # 一整块连续的 C 数组（Windows 上 l=4 字节）
t0 = time.perf_counter()
total = 0
for i in range(N):                         # 按行：地址连续
    for j in range(N):
        total += flat[i * N + j]
t_row = time.perf_counter() - t0
t0 = time.perf_counter()
total = 0
for j in range(N):                         # 按列：地址每次跳 N×4 字节 ≈ 4KB
    for i in range(N):
        total += flat[i * N + j]
t_col = time.perf_counter() - t0
print(f"array 按行 {t_row:.3f}s, 按列 {t_col:.3f}s")
```

预期输出（典型值）：

```text
array 按行 0.310s, 按列 0.560s
```

输出说明了什么：换成真连续内存后按列访问每步跨约 4KB（正好一页），缓存行整行作废；差距比列表版更干净。numpy 的大矩阵为什么快，除了 C 实现，「连续内存 + 列主序可选」也是一半功劳。

### 实验 3：顺序 vs 乱序

```python
# demo_random.py
import time, random, array

M = 4_000_000
a = array.array("l", range(M))     # 连续 ~16MB
idx = list(range(M))
random.shuffle(idx)                # 同样的下标集合，只是顺序乱了

t0 = time.perf_counter(); s = 0
for i in range(M):
    s += a[i]                      # 顺序：缓存行整块整块上车
t_seq = time.perf_counter() - t0
t0 = time.perf_counter(); s = 0
for i in idx:
    s += a[i]                      # 乱序：每步把缓存行扔掉换新的
t_rand = time.perf_counter() - t0
print(f"顺序 {t_seq:.3f}s, 乱序 {t_rand:.3f}s")
```

预期输出（典型值）：

```text
顺序 0.412s, 乱序 0.708s
```

输出说明了什么：访问集合完全相同，只乱序就慢出几十个百分点——这就是「链表遍历慢于数组」「哈希表比数组慢在访存」的微观原理。数据量越大、超过缓存容量越多，差距越大。

### 实验 4：stride 找拐点——缓存行「搭车」的边界

```python
# demo_stride.py
import time, array

N = 4_000_000
a = array.array("l", range(N))
for stride in (1, 2, 4, 8, 16, 32, 64):
    t0 = time.perf_counter(); s = 0
    for i in range(0, N, stride):   # 每次跳 stride 个元素
        s += a[i]
    print(f"stride={stride:>2}: {time.perf_counter() - t0:.3f}s")
```

预期输出（典型值）：

```text
stride= 1: 0.401s
stride= 2: 0.398s
stride= 4: 0.395s
stride= 8: 0.512s
stride=16: 0.589s
stride=32: 0.615s
stride=64: 0.637s
```

输出说明了什么：stride 1~4 时时间几乎不变——每个 64 字节缓存行（16 个 4 字节元素）还能捎带多次访问，访问数少了但都在同一行里；stride=8 起（Windows 上 4 字节元素、8 个正好跨两行）开始变慢，stride≥16 后每个缓存行只喂 1 次，多耗时基本恒定。**拐点位置 = 缓存行大小与元素大小的比值**——这是「缓存行 64 字节」最直观的实物证据。

## 常见坑

1. **坑 1：以为内存访问都一样快**。现象：热点循环怎么优化都不快。原因：一次未命中约 100ns，瓶颈在访存不在计算。排查：改成连续布局、减少指针追逐，往往立竿见影。
2. **坑 2：嵌套循环内外层顺序随手写**。现象：大数组上慢一个数量级，怎么都想不到原因。原因：最内层下标没沿内存方向连续变化。排查：让最内层下标沿行/主维度连续递增（C 风格数组沿行）。
3. **坑 3：以为加了缓存就一定快**。现象：把数据塞进「缓存友好」的容器却没变快。原因：随机访问模式（大哈希表、洗乱的指针数组）没有局部性，缓存帮不上还白搬。排查：先看访问模式是不是「成片」，再谈容器。
4. **坑 4：微基准没预热就被解释器开销掩盖**。现象：两次测量结果差 30%，看不出方向。原因：首次访问冷缓存、JIT/解释器波动、数组刚分配未触页。排查：先空跑一遍预热，多测取中位数，数组要足够大（超出缓存容量）效应才明显。
5. **坑 5：以为复杂度低就一定快**。现象：把 O(n) 数组求和换成 O(log n) 的树结构反而更慢。原因：树的节点在堆上乱跳，每个节点一次未命中；连续数组虽然 O(n) 但全命中。排查：估算「访问次数 × 命中率」，复杂度只是公式的一半。

## 小练习

1. 判断下列访问各体现哪种局部性：① 反复读写同一个计数器；② 遍历数组求和；③ 刚加载过的函数代码马上又被调用；④ 哈希表按随机 key 查 10 次。
2. 跑实验 1 并记录倍数；把 N 改成 2048 重跑——观察差距是否拉大，用「数据总量 vs 缓存容量」解释为什么更明显。
3. 跑实验 4，记录你的机器上的拐点出现在 stride 几；结合元素大小（`a.itemsize` 可查）算出缓存行大小，验证「拐点 = 64 字节 ÷ 元素大小」。
4. **综合排查任务**：同事把一个 2000×2000 网格的求和从按列改成按行，耗时从 2.1s 降到 0.3s。写一份 6 行诊断：① 用实验 1 复现并记录你的倍数；② 用缓存行机制解释倍数来源；③ 说明为什么 Python 里差距比 C 小（对象指针间接层）；④ 判断该网格改用 numpy 连续数组后还能再快多少、为什么；⑤ 给出「写数值代码先定布局再谈算法」的建议；⑥ 留一条「什么情况下按列反而该选列存储」的对照（提示：数据库列式存储是按查询场景选择布局）。
