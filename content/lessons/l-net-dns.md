> 一句话定义：DNS 是互联网的电话簿——把人记得住的 `www.baidu.com` 翻译成机器真正需要的 `110.242.68.4`。

## 概念讲解

### 为什么必须有翻译这一步

互联网上真正用来定位主机的是 IP 地址。IPv4 已经是一串不友好的数字，IPv6 更是一长串十六进制（`2001:db8:...`），人记不住；而域名是给**人**用的地址。所以浏览器发出 HTTP 请求之前，必须先完成一步：**域名 → IP**。

反过来说：**「上不了网」的故障里，有很大一部分根本不是网断了，而是「翻译失败」**。电话簿丢了不代表电话线断了——区分这两种故障，是 DNS 这课最重要的实用价值。

### 完整问路流程：六级缓存与三级服务器

查一个域名，系统按下面的顺序「问路」，每一级都可能直接给出答案、提前终止：

```text
① 浏览器缓存        刚访问过的域名，浏览器自己记着（几十秒~几分钟）
② 操作系统缓存      所有应用共享的系统级记录（hosts 文件也在这层生效）
③ 本地 DNS 服务器   运营商或你手动配置的（如 223.5.5.5 / 8.8.8.8）
      │ 它也没有时，替你走完剩下的三级：
      ├─ ④ 根服务器        「.com 这一片归谁管？」→ 交给 .com 顶级域
      ├─ ⑤ 顶级域服务器    「baidu.com 的记录在哪些服务器上？」→ 交给权威
      └─ ⑥ 权威服务器      域名主人的记录簿：「www = 110.242.68.4」
                       答案沿原路逐级返回，每一级顺手记进自己的缓存
```

根服务器全世界只有十几个「群组」，却撑起了全互联网——靠的就是**绝大多数查询在 ①②③ 就被缓存拦住了**，真正一路问到底的只有极少数。

### 层层缓存与 TTL：设计动机

全世界每秒几十亿次域名查询，如果每次都从根服务器问起，根服务器和权威服务器瞬间被打瘫。所以 DNS 的答案被设计成**可缓存的**，缓存多久由一个字段决定：**TTL（Time To Live，存活时间）**——域名主人可以设 60 秒，也可以设 86400 秒（一天）。

这是一笔经典的**新鲜度 vs 性能**交易：TTL 越长，缓存命中越多、解析越快、上游压力越小，但改动记录后全世界要等更久才能看到新答案。你在 nslookup 输出里能看到每个答案都带着 TTL 数字，还会**逐秒倒计时**——那是这条缓存记录的剩余寿命。

### 一张对照表：问路的每一层怎么查

把问路流程和排错工具对上号，DNS 故障就有了定位地图：

| 问到哪一层 | 怎么验证 | 这一层的常见故障 |
| ---- | ---- | ---- |
| ① 浏览器缓存 | 换无痕窗口再试 | 页面改版后仍看到旧页 |
| ② 系统缓存（含 hosts） | `ipconfig /displaydns`、直接 ping 域名 | hosts 被误改、缓存还没过期 |
| ③ 本地 DNS 服务器 | `nslookup` 顶部的「服务器」行 | 运营商劫持、配置了坏 DNS |
| ④–⑥ 根/顶级域/权威 | 用 DoH 查询对比公共 DNS 的答案 | 记录刚改、上游还在返回旧值 |

排错时按这张表从上往下问：**能越早一层拿到答案，故障就越靠近用户侧**——这也是为什么「先 flushdns 再怀疑全世界」是 DNS 排查的第一动作。

### 记录类型：电话簿里的不同条目

域名下的记录不止「域名→IP」一种：

| 类型 | 含义 | 典型用途 | 例子 |
| ---- | ---- | ---- | ---- |
| A | 域名 → IPv4 地址 | 最基本的解析 | `www.baidu.com → 110.242.68.4` |
| AAAA | 域名 → IPv6 地址 | IPv6 时代的双轨解析 | 同一域名同时有 A 和 AAAA |
| CNAME | 域名 → 另一个域名 | 把域名指向 CDN/服务商的地址，服务商怎么换你都不用改 | `www.example.com → cdn.example.net` |
| MX | 该域名收信的邮件服务器 | 发邮件时找收件方邮局 | `qq.com → mx1.qq.com` |
| NS | 该域名由哪些服务器解析 | 权威 DNS 在哪 | `baidu.com → ns*.baidu.com` |

最值得多看一眼的是 **CNAME**：它不是「翻译成 IP」，而是「翻译成另一个名字，再去查那个名字」——可能形成一条链。大型网站几乎都用它把流量交给 CDN，这也是为什么很多域名查出来「先多跳一个陌生名字」。

### 改解析为什么「要等一会儿」

域名主人在权威服务器上改了记录，为什么你这边半小时还看不到新 IP？因为**旧答案还躺在各级缓存里没过期**：你的浏览器缓存、系统缓存、本地 DNS 的缓存，都按旧 TTL 继续返回旧值。这就是运维圈的经典操作「**切流前先把 TTL 调短**」——提前 24 小时把 TTL 从一天改成 60 秒，等旧缓存过期，再真正改记录，全网几分钟内切换完毕。反过来，出事故想回滚时，也要等 TTL——**DNS 的生效时间由 TTL 决定，不由你决定**。

### DoH：给电话簿查询本身加密

传统 DNS 查询也是明文的，运营商可以看到（甚至篡改）你查了什么域名——这就是「DNS 劫持/广告注入」的来源。**DoH（DNS over HTTPS）**把查询装进 HTTPS 里：加密、防篡改，还能绕开运营商的本地 DNS 直接问公共 DNS。主流浏览器已默认启用，公共 DNS 服务商也都提供 DoH 接口，本课实验就会用到。

## 代码示例

主线任务：从「查一个 IP」走到「亲手劫持解析」，全程约 20 分钟。Windows 下在 PowerShell/Git Bash 运行；macOS/Linux 命令差异已标注。

### 第 1 步：基本查询——问出 IP

```bash
nslookup www.baidu.com
```

预期输出（Windows 节选）：

```text
服务器:  dns.example.local
Address:  192.168.1.1

非权威应答:
名称:    www.baidu.com
Addresses:  110.242.68.4
            110.242.68.3
```

逐行判读：

1. 顶部 `服务器/Address` 是**回答你的本地 DNS**（通常是你路由器或运营商的）；
2. `非权威应答` 说明答案是**从缓存里拿的**，不是直接问域名主人——你亲眼看到了「缓存层」在工作；
3. 一个域名出**多个 IP** 不是异常：那是负载均衡（多机房分流）。你访问时浏览器挑一个用，一个挂了换下一个。

### 第 2 步：查不同类型的记录

```bash
nslookup -type=CNAME www.baidu.com      # ① 别名记录
nslookup -type=MX qq.com                # ② 邮件服务器
nslookup -type=NS baidu.com             # ③ 谁是权威
```

预期判读：①会看到 `www.baidu.com → www.a.shifen.com` 这类「指向另一个名字」的答案——大型站点把流量交给 CDN 的痕迹；②返回几条带数字优先级的 `mx*.qq.com`（数字小者优先），这就是「发给 QQ 邮箱的信该送哪个邮局」；③列出的服务器正是 ① ② 的答案出处——**权威记录簿**。

### 第 3 步：DoH 查询——绕过本地缓存直接问公共 DNS

```bash
curl -s "https://dns.alidns.com/resolve?name=www.baidu.com&type=A"
```

预期输出（节选，JSON）：

```json
{
  "Status": 0,
  "Answer": [
    { "name": "www.baidu.com.", "type": 1, "TTL": 120, "data": "110.242.68.4" }
  ]
}
```

输出说明了什么：`Status: 0` 是 DNS 层面的「成功」；`Answer` 里 `type: 1` 就是 A 记录，`data` 是 IP，**`TTL` 是域名主人设定的缓存寿命**——你在第 1 步看到的倒计时，源头就是这里的这个数。对比两次查询，还能观察本地 DNS 与公共 DoH 返回的 IP 是否一致（不一致往往就是劫持或就近调度的线索）。

### 第 4 步：本机缓存实验——亲眼看 TTL 倒计时

```bash
ipconfig /displaydns | more     # Windows：翻看本机 DNS 缓存
```

预期看到：每条记录带 `TTL` 字段，**隔几分钟再看，数字在变小**——这就是缓存寿命在流逝，归零后这条记录会被删掉、下次重新问路。（macOS/Linux 没有等价单命令，可用 `sudo dscacheutil -statistics` 或跳过。）

顺手记住清缓存的标准动作（改 hosts、换 DNS 后必用）：

```bash
ipconfig /flushdns
# macOS: sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder
```

### 第 5 步：hosts 劫持实验——亲手改写解析

hosts 文件优先级**高于一切 DNS 服务器**（它属于问路流程第②层）。Windows 上**以管理员身份**打开记事本，编辑 `C:\Windows\System32\drivers\etc\hosts`（macOS/Linux 是 `/etc/hosts`，用 `sudo vi`），先备份原文件，然后加一行用一个**不存在的假域名**做实验：

```text
127.0.0.1  test.mylearn.local
```

保存后验证生效：

```bash
ping test.mylearn.local
```

预期输出：`来自 127.0.0.1 的回复`——这个域名根本不存在于任何 DNS，但它被解析成功了。输出说明了什么：**hosts 的优先级高于 DNS**，你刚刚亲手完成了一次「解析劫持」。生产排错里，hosts 被无意改过是「域名解析异常」的高频元凶。

再观察「解析成功 ≠ 网站能开」：

```bash
curl -sI http://test.mylearn.local
```

预期输出：`Failed to connect`（本机 80 端口没有服务在听）。判读：域名翻译这一步成功了，后面传输层和应用层照例要各答各的——呼应第一课的分层排查。

实验收尾：删掉这一行，然后 `ipconfig /flushdns`，再 `ping test.mylearn.local`——预期变为「未知主机」，因为假域名无处可解析了。**一生效一失效，两层缓存机制你都见过了**。浏览器如果表现顽固（仍用旧解析），重启浏览器再试。

## 常见坑

1. **坑 1：改了 hosts 却「不生效」**。现象：hosts 加了记录，浏览器照旧。原因：浏览器自身缓存了旧解析；或 hosts 没保存成功（Windows 用记事本直接保存会被权限拦下而不自知）。排查：先 `ping 域名` 确认系统层面是否生效，再 `ipconfig /flushdns` 并重启浏览器；确认是用「管理员身份」打开的编辑器保存的。
2. **坑 2：迁移服务器忘了调 TTL**。现象：换了新服务器，几小时后还有用户访问旧机器。原因：旧记录按长 TTL（如 86400 秒）缓存在全网各处。对策：提前把 TTL 调短到 60–300 秒，等旧缓存过期后再改记录——这是 DNS 运维的保命动作。
3. **坑 3：「ping 通 IP 打不开网站」把方向想反了**。现象：ping 域名不通就断定没网。原因：域名解析失败 ≠ 链路不通。排查：直接 `ping 一个已知 IP`——IP 通而域名不通，锅在 DNS（换 DNS 或查 hosts）；两个都不通才轮到查网络。
4. **坑 4：把「多个解析结果」当故障**。现象：nslookup 返回两个 IP 或先蹦出一个陌生 CNAME，以为被劫持。原因：多 IP 是负载均衡，CNAME 链是接入 CDN 的正常形态。排查：拿 DoH 查询对比公共 DNS 的答案，两边一致就不是劫持。
5. **坑 5：换 DNS 服务器立即测试，误判「没换成功」**。现象：改了系统 DNS 马上 nslookup，还是旧答案。原因：系统缓存与连接缓存还在。排查：先 `ipconfig /flushdns` 再测；测完可用 `nslookup www.baidu.com` 顶部「服务器」行确认回答者真的是新 DNS。
6. **坑 6：以为 DNS 只查 A 记录**。现象：排查邮件不通时 nslookup 只看到 IP。原因：邮件走 MX 记录、域名托管看 NS 记录、CDN 看 CNAME——每类问题查对应类型。排查：`nslookup -type=MX/NS/CNAME` 逐类验证。

## 小练习

1. 对三个常用网站各做 `nslookup` 和一次 DoH 查询，记录：解析出几个 IP、是否经过 CNAME、TTL 各是多少。
2. 查询 `qq.com` 的 MX 与 `baidu.com` 的 NS 记录，回答：发往 QQ 邮箱的信最后由哪台服务器接收？baidu.com 的权威解析由谁负责？
3. 完整重做第 5 步 hosts 实验：劫持生效 → 观察解析成功但连接失败 → 删记录 → flushdns → 验证失效，每步一句话记录现象。
4. **综合排查任务**：假设同事说「我们刚迁移了服务器，部分用户还访问到旧站」。写出完整排查步骤：用 nslookup / DoH 分别查当前解析结果，解释为什么两边可能不一致，给出「TTL、缓存、切换时机」三方面的处置建议。
