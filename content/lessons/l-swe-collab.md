> 一句话定义：feature 分支把每次改动隔离在自己的分支上，经 PR 评审后合入 main——改动有门，知识有广播，出事有据可查。

## 概念讲解

**先看反面：三个人直接 push main 会发生什么。** A 推了写到一半的半成品，B 构建「最新代码」时把半成品带上了线；C 改坏了一段逻辑，想回滚却发现和其他人的改动搅在一起，只能全仓库回滚。没有隔离，就没有「坏了也不影响别人」的保险。协作的起点不是工具而是共识：**main 上的每一行都应该是能上线的**。

**类比**：把 main 想成餐厅的「出品口」——只有通过检查的菜才能从这里端给客人。feature 分支是每道菜自己的备菜台，PR 是出品前的试菜环节：主厨之外的人尝一口，CI 这台检测仪验一遍，都点头才准出餐；合并后备菜台撤掉（删分支），下一道菜用新的台子。

**feature 分支工作流完整图解**（六步流水线）：

```text
        ①开issue      ②开分支       ③小步提交/推送    ④开PR        ⑤评审→修改      ⑥合并
main ──●──────────────●──────────────●───────────────●──────────────●───────────●──→ 时间线
         ＼              ＼            ＼               ＼             ＼
          #42 issue      fix/login      ●─●─●           讨论与CI       ●─● 修复后
          记录问题        -redirect      三个小提交                     再推送(自动更新)
```

固定节奏：**从最新的 main 出发 → 改动隔离在分支上 → 小步提交 → PR 打开讨论 → 评审通过合并 → 删分支**。分支是临时的：合完就删，长期不删的分支会腐烂，最后没人敢动。

**PR（Pull Request）的双重意义**——它不只是「请求合并」这个动作，而是两件完全不同的事：

1. **质量门（评审门）**：main 的最后一道关卡，别人看过、CI 绿了才准进。bug 在门口被拦下的成本是十分钟评论；混进 main 再被用户发现的成本是回滚加排查外加团队信任。评审门和 CI 课的自动检查是同一道门的两道锁：机器锁低级错误，人锁逻辑错误；
2. **知识存档（广播站）**：改动为什么这么写、当时讨论过哪些方案被否了，全留在 PR 页面里。三个月后有人问「这段逻辑为什么这样」，答案在 PR 评论里，而不是在离职同事的脑子里。新人翻 PR 历史也是最快的上手路径——等于读了一本带批注的教材。

**好 PR 三标准**，逐条展开：

| 标准 | 尺度 | 为什么 |
| ---- | ---- | ---- |
| 小 | 核心改动几百行内，评审人半小时能看完 | 评审质量随体积断崖式下跌：超过约 400 行，人就开始走马观花式点 approve |
| 单一目的 | 一个 PR 只解决一件事 | 修 bug 顺手重构三个模块，评审人无法聚焦，出问题也无法单独回滚 |
| 描述清楚 | 做什么 / 为什么 / 怎么验证 | 评审人第一眼看的是描述不是 diff——描述写不清，说明作者自己没想清 |

**单一目的的实操纪律**：改代码途中发现别的问题（顺手看到的错别字、想优化的旧逻辑），**忍住**——记一个新 issue，另开分支另开 PR。PR 页面里混进第二件事的那一刻，评审质量就开始崩塌。

**PR 描述好坏对照**（同一次改动的两种写法）：

```markdown
<!-- 差：评审人只能靠猜 -->
更新代码
修了一些 bug，顺便改了登录

<!-- 好：三问齐答 + 关联 issue -->
## 做了什么
登录成功后跳回来源页，而不是固定回首页。

## 为什么
closes #42（用户反馈：从文章页登录后被扔回首页）

## 怎么验证
新增 test_login_redirect，覆盖 3 种来源页场景；本地手动回归通过。
```

**Code Review 看什么**——三层清单，从重到轻，顺序不能乱：

1. **正确性**：逻辑对不对？边界考虑了吗（空输入、失败路径、并发）？有没有更简单的写法达到同样效果？这是评审的核心价值——作者往往被自己的思路锁住，恰恰看不出这里；
2. **可读性**：三个月后的别人能否看懂？命名达意吗？函数是否过长？有没有该提取的重复逻辑？
3. **测试覆盖**：新逻辑有没有测试钉住？修 bug 是否附带了能复现这个 bug 的测试？（呼应测试课：钉住 bug 的测试是回归保护。）

分层的意义在于**先重后轻**：正确性没过的 PR，讨论缩进毫无意义。而**风格问题（缩进、引号、分号）不在清单上**——那是格式化工具的活（呼应代码规范课），人肉 diff 逐行挑格式既浪费时间又伤感情。

**评论礼仪**——评审的目的是让代码更好，不是证明 reviewer 高明：

| 原则 | 反例 | 正例 |
| ---- | ---- | ---- |
| 对事不对人 | 「你这里写错了」 | 「这里按下标取单价，字段顺序一变会静默出错」 |
| 提问式建议 | 「必须改成解构」 | 「要不要改成解构？字段顺序变化时更稳」 |
| 说明理由 | 「这样不行」 | 「这样在跨时区场景会差一天，建议统一用 UTC」 |

前瞻性意见（不影响本次合并、但值得记下）加前缀 `nit:` 或 `future:`，例如「nit: 这个函数名可以更直白，不阻塞合并」——**把「必须改」和「顺便提一嘴」分开**，作者才有清晰的行动信号；反过来，把安全问题的「必须改」也说成商量口气，就拦不住危险改动。

**分支策略光谱**——三个常见流派放在一起看：

| 策略 | 分支结构 | 优点 | 代价 | 适合 |
| ---- | ---- | ---- | ---- | ---- |
| 主干开发（trunk-based） | 人人高频小步合入 main | 集成早、冲突小 | 未完成功能靠特性开关藏起来 | 工程成熟度高的团队 |
| GitHub Flow（本课） | main + 短命 feature 分支 | 简单、够用 | 发布节奏需另管 | 小团队、持续部署 |
| Git Flow | main/develop/release 多条长期分支 | 版本发布可控 | 流程重、合并成本高 | 固定版本发版的客户端软件 |

小团队从 GitHub Flow 起步最省心：它相当于「主干开发的保守版」——保留分支隔离与评审门，只是没有多套长期分支。等团队变大、发布变复杂，再考虑加重流程。

**issue 与 PR 关联**：在 PR 描述里写 `closes #42`（同义写法 fixes/resolves #42），PR 合并进默认分支时 GitHub 自动关闭对应 issue。这条小语法串起的是**可追溯链**：issue 记「为什么做」→ PR 记「怎么做的、怎么评的」→ commit 记「改了哪几行」。出事回溯、新人考古，都顺着这条链走。

## 代码示例

主线：**模拟一次完整协作**——修一个真实感的 bug，从 issue 到合并全流程走一遍。在自己的仓库上演练即可；单人也能走完整流程，给自己提 PR、自己评审自己（重点是把每一步的角色感走出来）。

**第 1 步：开 issue，把问题写清楚**（网页点 New issue，或用 GitHub CLI）：

```bash
gh issue create \
  --title "从文章页登录后跳回首页" \
  --body "复现：在文章页 /posts/12 点登录，成功后回到首页而非文章页。
期望：跳回登录前的来源页。"
```

【截图位】issue 页面：标题 + 复现步骤 + 期望行为，三段齐全，编号 #42 由 GitHub 自动分配。

**第 2 步：从最新 main 开 feature 分支**：

```bash
git switch main && git pull          # 先同步，从最新 main 出发
git switch -c fix/login-redirect     # -c 创建并切换；名字 = 类型/目的
```

分支命名习惯：`fix/` 修 bug、`feat/` 新功能、`chore/` 杂务——名字让人不看代码也知道分支在干什么。

**第 3 步：小步提交**。每完成一个可独立描述的小块就 commit：

```bash
git add src/auth/redirect.js
git commit -m "登录成功后跳回来源页而非首页"

git add src/auth/redirect.js
git commit -m "来源页为外域时降级回首页"    # 边界处理单独一个提交
```

**第 4 步：推送并创建 PR**：

```bash
git push -u origin fix/login-redirect   # -u 建立跟踪关系，之后 git push 即可
gh pr create --fill                     # 或网页上点 Compare & pull request
```

PR 描述套概念课的好模板，结尾关联 issue：

```markdown
## 做了什么
登录成功后跳回来源页（document.referrer），外域来源降级回首页。

## 为什么
closes #42（用户反馈：从文章页登录后被扔回首页）

## 怎么验证
新增 test_login_redirect 覆盖 3 种来源场景；本地手动回归通过。
```

【截图位】PR 页面 Conversation 标签：描述、diff、底部的 CI 检查状态（黄点转绿勾）。

**第 5 步：收到评审意见**。两条典型评论长这样：

```text
reviewer-a：
  直接取 document.referrer 的话，来源为空时它是什么值？
  要不要加一个空值降级？                        ← 提问式，指向边界情况

reviewer-b：
  nit: getLoginTarget() 这个名字可以更直白，
  比如 resolveRedirectUrl()。不阻塞本次合并。    ← 前瞻性意见，标了 nit
```

【截图位】Files changed 标签：行内评论悬停在具体代码行上，可逐条回复。

**第 6 步：回应与修改**。修改不需要新开 PR——**往同一分支 push，PR 自动更新**：

```bash
# 修复 reviewer-a 指出的空值边界
git add src/auth/redirect.js
git commit -m "referrer 为空或外域时降级回首页"
git push                                  # PR 页面自动多出这个提交
```

回到 PR 页面逐条回复评论（「已修复，见 xxx 提交」），修完点 Re-request review 请评审人再看一眼。nit 那条可改可不改，但**要么照做要么回复说明**，留白不礼貌。

**第 7 步：合并**。CI 绿 + 评审 approve 之后执行合并：

```bash
gh pr merge --squash --delete-branch      # squash 合并并删除远端分支
git switch main && git pull               # 本地回到最新 main
```

squash 会把分支上的多个小提交压成 main 上的一个干净提交——分支内保留过程，主干只留结果。

**第 8 步：验证可追溯链**。回到 issue #42：状态已自动变成 Closed，时间线里挂着合并它的那个 PR。issue（为什么做）→ PR（怎么改、怎么评）→ commit（改了哪几行），一条链完整走通。

【截图位】issue #42 的时间线最下方：closed this in #43。

## 常见坑

1. **坑 1：分支养两周，攒 47 个文件再开「巨型 PR」**。评审人看不动只能秒批，评审形同虚设，出问题也没法单独回滚。排查信号：PR 打开超过 3 天没人评、diff 长到要点「加载更多」。对策：一个分支活一天以内，按目的切片，小步勤开 PR。
2. **坑 2：从旧 main 开分支，合并前不更新**。开发一周后 PR 的 diff 里突然多出「别人的改动」——其实是分支落后于 main 的反向 diff，冲突爆发。对策：开工前 `git pull`；长期分支定期合并或 rebase 到最新 main 再继续。
3. **坑 3：评审变抬杠**。盯着分号、引号这类工具能管的事写十几条评论，正确性反而没人看。对策：按三层清单先重后轻，格式问题让格式化工具闭嘴。
4. **坑 4：LGTM 秒批**。diff 太大看不完又不好意思卡着，就点 approve——评审门被架空，坏代码照样进 main。对策：太大就明说「请拆小」，秒批不如不批。
5. **坑 5：评论对人不对事**。「你怎么又用 for 循环」会让评审变成防御战。对策：评论的主语永远是代码不是人——「这段在空列表时会抛错」比「你总忘了判空」有效得多。
6. **坑 6：一个 PR 塞多个目的**。「修 bug 顺手升级依赖顺便重构」——单一目的被破坏，评审聚焦失效。对策：忍住顺手改的冲动，新问题开新 issue、走新分支。

## 小练习

1. 在 GitHub 上找一个开源项目已合并的小 PR，对照三标准（小 / 单一目的 / 描述清楚）逐条打分，再看它的评审评论里有没有 `nit:` 这类标注。
2. 给你最近的一次改动写一份完整 PR 描述（做什么 / 为什么 / 怎么验证），并先开一个 issue，用 `closes #n` 关联起来。
3. 综合任务：完整走一遍本课主线——自己建仓库、开 issue、开分支、给自己提 PR，然后切到网页端给自己留一条提问式评审意见、修复、squash 合并，最后确认 issue 自动关闭。
4. 思考题：为什么「小 PR」不只是礼貌，还能降低 bug 混进 main 的概率？（提示：评审质量随体积怎么变化？评审人的注意力预算是多少分钟？）
