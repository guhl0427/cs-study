> 一句话定义：CPU 是个只会循环干四步的工人——取指、译码、执行、写回；程序就是喂给它的指令序列，而「跳转」不过是改了它手里记录下一站的地址（PC）。

## 概念讲解

### CPU 内部三大件

类比一个流水线工人，三个部件缺一不可：

| 部件 | 类比 | 干什么 |
| ---- | ---- | ---- |
| 寄存器 | 随身口袋 | 存正在计算的几个数，全机最快，只有十几个 |
| ALU | 手和工作台 | 只会加减乘、位运算这些「小活」，快得惊人（亚纳秒级） |
| 控制单元 | 读工单的大脑 | 读指令、拆指令、指挥另外两个部件按顺序干活 |

寄存器为什么只有十几个还要单独强调？因为它是**唯一快到能跟上 CPU 的存储**——内存比它慢百倍（下一课细算这笔账）。编译器的核心工作之一，就是安排「什么数据在口袋里、什么时候腾出去」。

### 指令：操作码 + 操作数

指令是一串机器数：**操作码（干什么）+ 操作数（对谁干）**。x86 上 `add eax, 5` 编码成三个字节 `83 C0 05`——你眼里的汇编是人给字节起的助记名，CPU 眼里只有数字。程序、字节码、汇编、机器码都是同一件事的不同抽象层：**都是「操作码+操作数」的序列**，只是执行者不同（硬件 CPU 或软件解释器）。

### 取指 → 译码 → 执行 → 写回：CPU 的全部日常

```text
      ┌─────────────────────────────────────────────────┐
      │                                                 │
      ▼                                                 │
① 取指：按 PC 里的地址，从内存把指令拿回来                  │
      ↓                                                 │
② 译码：控制单元拆出「操作码 + 操作数」                     │
      ↓                                                 │
③ 执行：ALU 算 / 按地址读写内存                             │
      ↓                                                 │
④ 写回：结果放回寄存器；PC 自动 +1 指向下一条 ────────────────┘

跳转指令（jmp / jl / call / ret）：不干活，只把 PC 改成别的地址
—— 循环、if、函数调用从此成为可能
```

**程序计数器（PC）**存着「下一条指令的地址」：顺序执行时自动前进，而 `if`、`while`、函数调用的本质，都是某条指令把 PC 改走。循环就是「跳回开头」那条指令每轮都成立；现代 CPU 的**分支预测**会赌你往哪个方向跳（猜对了零成本，猜错了清空流水线重来）——这是为什么排序好的数组跑 if 会更快的冷知识。

### 汇编直觉表

| 汇编（x86 直觉版） | 意思 | 对应高级语言 |
| ---- | ---- | ---- |
| `mov eax, [x]` | 把变量 x 取进口袋 | 读变量 |
| `add eax, 1` | 口袋里的数加 1 | `x = x + 1` |
| `cmp eax, 10` | 比一比（不改值，只设标志位） | `if` 的比较部分 |
| `jl loop` | 小于就跳回 | `while` 的回跳 |
| `call f` / `ret` | 跳去函数 / 跳回原地 | 函数调用与 return |
| `push` / `pop` | 压栈 / 出栈 | 栈帧的搭建与拆除 |

认得这六条，你就能读懂大多数函数的汇编骨架——剩下的查手册即可，不需要背指令集。

### 函数调用栈帧：局部变量的硬件现场

每次 `call` 都会在栈上压出一块**栈帧**：返回地址、参数、局部变量的临时住所。

```text
高地址 ┌────────────────┐
       │ 调用者的栈帧     │
       ├────────────────┤ ← rbp（当前帧基址）
       │ 返回地址        │ ← call 自动压入：ret 就靠它跳回去
       │ 保存的旧 rbp    │ ← 方便回来后恢复现场
       │ 参数 n          │ ← 调用约定决定放寄存器还是放栈
       │ 局部变量 sum    │ ← 「局部变量住在栈上」的硬件现场
       ├────────────────┤ ← rsp（栈顶，向下生长）
低地址 │ （下一层栈帧…）  │ ← 递归 = 栈帧叠栈帧
```

这正好呼应 C 指针课的两句话：局部变量（自动变量）确实住在栈上、函数返回后栈帧回收所以不能返回局部变量的地址。栈空间有限（默认几 MB），递归太深把栈叠满就是**栈溢出**——Python 里表现为 `RecursionError`（解释器主动设了 ~1000 层的保险），C 里直接段错误。

### 为什么 C 快：翻译级数差

```text
C：      源码 ──编译器（运行前一次性翻译）──→ 机器指令 ──CPU 直接执行
         一行代码 ≈ 几条指令，运行时零中间层

Python： 源码 ──→ 字节码 ──→ 解释器循环逐条分发（解释器本身是一段 C 程序）
                              ↑ 每条字节码都要再经历「取指-译码-分发-跳转」
                                一行 Python 往往是几十上百条机器指令
```

同样的求和循环，C 编译后是几条指令的小循环；Python 每次迭代要跑解释器的分发逻辑十几步。差一个数量级是常态，热点循环差两个数量级也不稀奇。Java/C# 介于两者之间（先翻译成字节码，运行时 JIT 再把热点翻译成机器码）。这就是「Python 写原型、C/Rust 写热点」的行业惯例的全部理由。

## 代码示例

主线任务：用 dis 解剖字节码 → 找出条件跳转与回跳 → gcc -S 看真机器 → 数一条语句的指令账。全程约 35 分钟。

### 实验 1：dis.dis 第一次解剖

```python
# demo_dis.py
import dis

def add_ten(n):
    return n + 10

dis.dis(add_ten)
```

预期输出（3.11+，地址列略去）：

```text
  LOAD_FAST  0 (n)      → 取参数 n 进「口袋」
  LOAD_CONST 1 (10)     → 取常量 10
  BINARY_OP  0 (+)      → 相加
  RETURN_VALUE          → 返回
```

输出说明了什么：四条指令全部是「操作码 + 操作数」——字节码和机器码同构，只是执行者从硬件换成了软件解释器。`LOAD_FAST` 的 FAST 指局部变量走快速通道；对比 `LOAD_GLOBAL` 会慢一截（要查两级命名空间），这是「少用全局变量」的性能理由。

### 实验 2：找出 if 的条件跳转与 while 的回跳

```python
def grade(n):
    if n >= 60:
        return "及格"
    return "不及格"

dis.dis(grade)
```

预期输出（节选，3.11+）：

```text
  LOAD_FAST  0 (n)
  LOAD_CONST 1 (60)
  COMPARE_OP 5 (>=)
  POP_JUMP_FORWARD_IF_FALSE  → 跳到 L1      ← if 的本质：条件跳转
  LOAD_CONST 2 ('及格')
  RETURN_VALUE
L1: LOAD_CONST 3 ('不及格') …
```

```python
def countdown(n):
    while n > 0:
        n -= 1
    return n

dis.dis(countdown)
```

预期输出（节选）：

```text
  … LOAD_FAST n / LOAD_CONST 0 / COMPARE_OP >（比较）
  POP_JUMP_FORWARD_IF_FALSE → 跳到出口      ← 条件不成立才跳出
  … n -= 1 的几条指令 …
  JUMP_BACKWARD → 跳回上面                  ← while 的本质：跳回开头
```

输出说明了什么：if = 条件跳转，while = 条件跳转 + 无条件回跳，与概念讲解的 PC 图完全对应（3.10 及更早版本指令名是 `POP_JUMP_IF_FALSE`/`JUMP_ABSOLUTE`，看名字就能对上）。CPU 层面的等价物是 `cmp` + `jl`——高级语言的控制流在机器层只是改 PC。

### 实验 3：gcc -S 看真机器（Windows 没 gcc 就用 godbolt.org）

```bash
echo 'int square(int n){return n*n;}' > sq.c
gcc -O0 -S sq.c -o sq.s && cat sq.s        # -S：停在汇编这一步，-O0：不优化
gcc sq.c && objdump -d a.out | grep -A8 '<square>'   # 反汇编：看机器码字节
```

`sq.s` 关键部分（x86-64，AT&T 语法）：

```text
square:
    pushq   %rbp                # 保存上一层栈帧基址：栈帧开始搭建
    movl    %edi, -4(%rbp)      # 参数 n 落进栈帧（edi 是传参寄存器）
    movl    -4(%rbp), %eax      # 取进口袋 eax
    imull   %eax, %eax          # eax = eax * eax —— 真正干活的只有这条
    movl    %eax, -8(%rbp)      # 结果存回局部变量（-O0 的呆板：每步都过内存）
    movl    -8(%rbp), %eax      # 再取回准备返回
    popq    %rbp                # 恢复上一层栈帧
    ret                         # 按 call 压好的返回地址跳回去
```

判读：push/pop/rbp 正是栈帧图的实物；`-O0` 下连乘法结果都要先写内存再读回来。把第一条命令的 `-O0` 改成 `-O2` 再看：只剩 `imull` 和 `ret` 两三条——编译器把一切搬运都省了。**同一段代码，优化前后指令数差几倍，这就是 release 版比 debug 版快的微观原因。**

### 实验 4：数一数一行 Python 的指令账

```python
import dis

def loop():
    total = 0
    for i in range(1_000_000):
        total += i
    return total

print("字节码指令条数：", len(list(dis.get_instructions(loop))))
# 典型输出：22 条左右 —— 其中循环体每轮要重跑约 8 条
# 100 万次迭代 × 8 条字节码，每条字节码又对应解释器 C 循环里的几十条机器指令
# —— 这就是「Python 慢」的完整账本：不是算法差，是翻译级数多
```

输出说明了什么：把「为什么 C 快」从感觉变成数字。想更狠一点：同一函数用 C 写、godbolt 编译，数出机器指令只有 5 条左右，且 CPU 直接执行——没有中间分发层。这组数字就是「原型用 Python、热点下沉 C/numpy」的量化依据。

## 常见坑

1. **坑 1：以为「一行代码 = 一条指令」**。现象：按行数估算性能，方向全错。原因：一行 Python/C 往往对应几条到几十条机器指令。排查：用 `dis` 或 godbolt 看翻译结果，按指令数和访存次数估成本。
2. **坑 2：被 AT&T 汇编语法劝退**。现象：看一眼 `movl %edi, -4(%rbp)` 就放弃。原因：AT&T 源在前目的在后、满眼 `%` `$`，与 Intel 手册相反。排查：godbolt 右上角切换 Intel 语法（`mov dword ptr [rbp-4], edi`），观感立刻友好。
3. **坑 3：以为 CPU 慢在计算**。现象：优化算法后仍然慢。原因：ALU 加法不到 1ns，瓶颈常在访存和分支——取指慢、缓存未命中、分支预测失败。排查：这正是下一课缓存的主题，先记住「算得快不等于跑得快」。
4. **坑 4：递归无底撞栈**。现象：Python 报 `RecursionError`，C 直接段错误。原因：每次调用压一层栈帧，栈默认只有几 MB。排查：检查递归出口；改写循环或尾递归；Python 可用 `sys.setrecursionlimit` 放宽但栈真满了照崩。
5. **坑 5：拿 -O2 的汇编学机器码**。现象：自己写的代码编出来汇编面目全非、变量全消失。原因：编译器把能省的都省了（常量折叠、指令合并），学阶段看不懂。排查：先用 `-O0` 对照学习，理解后再看 `-O2` 体会优化。

## 小练习

1. 给 `grade` 增加 90 分以上的「优秀」分支，用 `dis.dis` 找出全部条件跳转指令；再写一个等价的 `while` 版本，确认每个循环都有一个 `JUMP_BACKWARD`。
2. 在 godbolt 上编译 `int diff(int a, int b){return a - b;}`：指出减法指令，并说明参数 a、b 分别从哪个寄存器进来（提示：x86-64 传参寄存器顺序 edi、esi…）。
3. 栈溢出实验：写一个无出口的递归函数，分别体验 Python 的 `RecursionError` 和（若装了 gcc）C 版的段错误；打印/观察递归层数，解释「栈帧叠满」与上一节栈帧图的关系。
4. **综合排查任务**：团队的求和服务 Python 版跑 100 万条数据要 8 秒，C 版只要 0.15 秒。写一份 6 行诊断：① 用 `dis.get_instructions` 数出循环体字节码条数；② 用 godbolt 数出 C 循环体机器指令条数；③ 解释两个数量级的来源（翻译级数）；④ 给出「热点下沉」的三个选项（C 扩展 / numpy 向量化 / 纯算法改造）；⑤ 说明为什么 numpy 能到接近 C 的速度；⑥ 留一条何时「不值得下沉」的判断标准。
