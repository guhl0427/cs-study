> 一句话定义：机器里的一切信息都是 0 和 1——二进制是硬件的母语，补码让加法器顺手算负数，IEEE 754 用近似值换小数；读懂这三件事，就看懂了机器眼里的数字。

## 概念讲解

![二进制、十六进制与十进制的对应](fig:co-bits)

### 为什么是二进制

电路里最可靠的区分不是「电压多高」，而是「有没有电」：晶体管只有**导通/截止**两个稳定状态。类比：识别「灯亮/灯灭」几乎不会出错，识别「灯的十档亮度」稍一抖动就认错档位。要是用十个电压档直接表示十进制，信号一点噪声就串档；两个状态却容错性极强——所以计算机从底层就选定二进制，一切信息（数字、负数、小数、文字、图片）都要先翻译成 0 和 1 才能进门。

### 十六进制：二进制的缩写记法

二进制写起来太长，人类发明了十六进制当「缩写」：**一位十六进制正好对应 4 位二进制**，一个字节（8 位）正好写成两位十六进制。

| 十进制 | 二进制    | 十六进制 | 拆解 |
| ------ | --------- | -------- | ---- |
| 5      | 0101      | 0x5      | 4 位一组 |
| 10     | 1010      | 0xA      | A=1010 |
| 15     | 1111      | 0xF      | 一组能表示的最大值 |
| 255    | 1111 1111 | 0xFF     | F+F：两个「满格」 |

看抓包工具里的 `CA`、配色码里的 `#RRGGBB`、调试器里的内存十六进制转储，本质上都在读二进制的缩写。换算直觉记一条：2^10 = 1024 ≈ 10^3，所以 1 KB ≈ 一千字节，2^20 ≈ 1M，2^32 ≈ 4G——「约 1000 倍」的直觉够日常用，报配置时才分清两种进位。

### 补码完整推演：一个会绕圈的里程表

**负数怎么表示？** 把 8 位比特想成一个 256 格的循环里程表：里程表转到头就绕回起点，没有「正负」标记，但 0 减 5 与 251 加 5 落在同一个格子上——**用绕圈的方式表达减法**。

```text
8 位里程表（256 格，顺时针加 1）：
  0111 1111 =  127   ← 最大值（最高位 0：正数区）
  0000 0001 =    1
  0000 0000 =    0
  1111 1111 =   -1   ← 最高位 1：负数区（越界绕回）
  1111 1100 =   -4
  1000 0000 = -128   ← 最小值
```

- **范围**：256 格分两半，正数区 0~127 占 128 格，负数区 -1~-128 也占 128 格，所以 8 位补码范围是 **-128~127**，且不对称——0 占掉了正区一格，-128 没有对应的 +128。
- **求负数**：取反加一。5 = 00000101 → 取反 11111010 → 加 1 → 11111011，这就是 -5 的机器码（也等于 256-5=251）。
- **加法电路不认符号**：251+5 = 256，第 9 位进位被硬件丢弃，剩下 0 = -5+5 ✓；251+254 = 505，丢掉 256 剩 249，而 249 的补码正是 -7 ✓。**一套加法电路通吃加减法**——这就是补码统治所有主流 CPU 的原因：硬件简单就是一切。
- **溢出**：127+1 → 10000000 = -128。正数区加穿了会「绕」到负数区，因为 8 位根本装不下 128——这不是 bug，是里程表的物理本性。

### 位数与范围速查

补码的范围公式：n 位有符号整数的范围是 **-2^(n-1) ~ 2^(n-1)-1**，任何位数都不对称——0 永远占掉正区一格：

| 位数 | 无符号范围 | 有符号（补码）范围 | 常见名字 |
| ---- | ---- | ---- | ---- |
| 8 | 0~255 | -128~127 | byte / signed char |
| 16 | 0~65535 | -32768~32767 | short |
| 32 | 约 43 亿 | 约 ±21.5 亿 | int |
| 64 | 约 1.8×10^19 | 约 ±9.2×10^18 | long / long long |

这张表是踩溢出坑前的最后防线：Java 的 int 溢出、数据库列类型选错、C 的 `signed char` 越界，都源于「没对表」。位数直觉一条：每加一位范围翻倍——2^10 ≈ 10^3，所以 32 位约 4×10^9，64 位约 1.8×10^19。

### IEEE 754：用近似值换小数

浮点数存成「**符号 + 指数 + 尾数**」，相当于二进制版的科学计数法（float32 分 1+8+23 位，double 分 1+11+52 位）。麻烦在于：0.5、0.25 这类 2 的负次幂能精确存，但 0.1 在二进制里是 0.00011001100110011… 的**无限循环**——就像十进制写 1/3 = 0.333… 永远写不完，只能截断成近似值。

0.1 和 0.2 各带一点误差，两个近似值相加的结果恰好落在 0.3 近似值的隔壁——这就是 `0.1 + 0.2 != 0.3`。它不是 Python 的 bug，也不是「CPU 随机误差」：每次运行都精确地得到同一个 0.30000000000000004，误差是编码方式**固有的、确定的**。

| | 整数（补码） | 浮点（IEEE 754） |
| ---- | ---- | ---- |
| 精确性 | 范围内绝对精确 | 范围极大但普遍近似 |
| 适合存 | 计数、金额（用「分」） | 测量值、科学计算、统计 |
| 能否用 == 比较 | 能 | 不能，要用容差 |
| 溢出行为 | 定宽类型绕圈（-128 出口） | 变成 inf/NaN |

### 字符编码一句话

ASCII 用一个字节表示英文字母与符号（'A'=65）；UTF-8 是兼容 ASCII 的**变长**编码——英文 1 字节、常用汉字 3 字节，它是今天互联网的通用格式。「乱码」的物理本质：同一串字节用错误的编码规则去解（或者编码与解码没配对）。本课的主战场是数字，编码课再展开。

## 代码示例

主线任务：三进制换算 → 用 & 0xFF 逼出补码真身 → 位运算实用三招 → 浮点真身与安全用法 → 字符编码一探。全程约 25 分钟。

### 实验 1：bin / hex / int 三向换算

```python
print(bin(202))              # 0b11001010 —— 0b 前缀表示二进制
print(hex(202))              # 0xca —— 0x 前缀表示十六进制
print(int("11001010", 2))    # 202：按二进制读字符串
print(int("ca", 16))         # 202：按十六进制读
print(0b11001010 == 0xCA == 202)   # True：同一个数的三种写法
print(bin(int("c", 16)), bin(int("a", 16)))  # 0b1100 0b1010 —— C 和 A 各自就是 4 位
```

预期输出说明：最后一行验证「缩写」关系——把 0xCA 拆成 C=1100、A=1010，两位十六进制拼回去就是 8 位二进制。以后看任何十六进制数，先在心里 4 位一组展开，内存转储就不再神秘。

### 实验 2：用 & 0xFF 逼出补码真身

```python
print(bin(-5))                # -0b101 —— 这是给人看的写法，不是机器里的比特
a = -5 & 0xFF                 # 0xFF 当「8 位镜子」：截出最低 8 位
print(bin(a))                 # 0b11111011 —— 这才是内存里 -5 真正的样子
print((a + 5) & 0xFF)         # 0 —— 251+5=256，进位丢弃，正好 -5+5=0
print((a + 254) & 0xFF)       # 249，而 249 的补码正是 -7 —— 加法器全程没管符号
print(bin((127 + 1) & 0xFF))  # 0b10000000 —— 127+1 溢出成 -128
print(-128 & 0xFF)            # 128，二进制 10000000 —— 最小值没有对应正数
```

预期输出说明：`-5 & 0xFF` 得 251，二进制 11111011——与概念讲解的取反加一推演完全一致。两行加法验证「电路不认符号」：251 加什么丢进位后等于几，补码解释下就是 -5 加几。溢出行则演示里程表绕圈：正区加穿，出口落在 -128。

### 实验 3：位运算实用三招

```python
x = 202
print(x & 1)          # 0 —— 判断奇偶：最低位 0 是偶数（比 x % 2 更贴硬件）
print(x >> 1)         # 101 —— 右移一位 = 整除 2
print(x << 1)         # 404 —— 左移一位 = 乘 2
print(x & 0xF)        # 10 —— 掩码取低 4 位（等价 x % 16）
print(x & 0xFF == 10) # False —— 坑来了：== 优先级高于 &，实际算的是 x & (0xFF == 10)
print((x & 0xFF) == 10)  # True —— 位运算和比较混用时永远加括号
```

预期输出说明：位运算是直接操作比特的工具——网络编程的子网掩码、协议解析里的标志位、哈希函数，全是它们的用武之地。倒数两行是真实存在的语言级陷阱：`&` 的优先级低于 `==`，不加括号语义完全变了。

### 实验 4：浮点真身与安全用法

```python
import math

print(0.1 + 0.2)                # 0.30000000000000004
print(0.1 + 0.2 == 0.3)         # False
print(format(0.1, ".55f"))      # 0.1000000000000000055511151231257827021181…
print(format(0.5, ".55f"))      # 0.50000000000000000 —— 2 的负次幂，精确！
print(format(0.25, ".55f"))     # 0.25000000000000000 —— 精确
print(math.isclose(0.1 + 0.2, 0.3))   # True —— 比较浮点要用容差

total = 0.0
for _ in range(1000):
    total += 0.1                # 「一毛钱」累加 1000 次
print(total)                    # 99.9999999999986 —— 不是 100！

cents = 0
for _ in range(1000):
    cents += 10                 # 用整数「分」记账（0.1 元 = 10 分）
print(cents / 100)              # 100.0 —— 分毫不差
```

预期输出说明：`.55f` 把尾数的「藏着的误差」打印出来——0.1 存进去的本来就不是 0.1；0.5/0.25 精确是因为分母是 2 的幂。累加实验给了金额问题的标准答案：**浮点做测量，整数做账本**。

### 实验 5：字符编码一探

```python
print(ord("A"), ord("中"))                  # 65 20013 —— 码点（编号）
print("A".encode("utf-8"))                  # b'A' —— 1 字节
print("中".encode("utf-8"))                 # b'\xe4\xb8\xad' —— 3 字节
print(len("中"), len("中".encode("utf-8"))) # 1 3 —— 字符数 ≠ 字节数
print(b'\xe4\xb8\xad'.decode("utf-8"))      # 中 —— 解码必须用同一套规则
```

预期输出说明：一个汉字在「字符数」的世界里是 1，在「字节」的世界里是 3——截断、计费、网络包长都按字节算，字符数与字节数混淆是乱码和截断半字的直接来源。

### 实验 6：自己写一个十进制转二进制的换算器

```python
def to_bin(n):
    bits = []
    while n > 0:
        bits.append(str(n % 2))     # 除 2 取余：余数就是当前最低位
        n //= 2
    return "".join(reversed(bits)) or "0"

for v in (5, 10, 202, 255):
    print(v, "->", to_bin(v), "与内置一致：", bin(v)[2:] == to_bin(v))
```

预期输出：

```text
5 -> 101 与内置一致： True
10 -> 1010 与内置一致： True
202 -> 11001010 与内置一致： True
255 -> 11111111 与内置一致： True
```

输出说明了什么：「除 2 取余、倒序拼接」就是二进制的定义本身——10 = 1 个 8 + 0 个 4 + 1 个 2 + 0 个 1。亲手写一遍后 `bin()` 不再是黑盒，换算也变成纸笔可做的动作。

### 实验 7：大数吃小数——IEEE 754 的另一个坑

```python
big = 1e16
print(big + 1.0 == big)        # True —— 1.0 加不进去
print(big + 1.0 + 1.0 - big)   # 0.0 —— 连加两个 1 也白加
print(big + 2.0 - big)         # 2.0 —— 但 2.0 加得进去
```

预期输出：

```text
True
0.0
2.0
```

输出说明了什么：float64 只有 52 位尾数，1e16 量级相邻两个可表示值正好差 2——加 1 落在缝里被「吃掉」。这就是「加法顺序不同结果不同」的根源：浮点加法不满足严格结合律，统计累加要用分块求和或高精度类型。

## 常见坑

1. **坑 1：买了 1TB 硬盘只显示 931GB**。现象：以为被虚标了。原因：厂商按 1000 进位、操作系统按 1024 进位。排查：先弄清当前场合的进位约定，2^10=1024 只是「约等于 1000」。
2. **坑 2：拿 Python 的 `bin(-5)` 理解补码**。现象：看到 `-0b101` 以为机器里存的是「负号+101」。原因：那是给人看的带符号写法，不是比特真身。排查：n 位整数就用 `bin(-5 & (2**n - 1))` 看 8/16/32 位补码。
3. **坑 3：浮点直接 `==` 比较、拿 float 存钱**。现象：账目对不平、循环判断永远差一点。原因：IEEE 754 固有近似，换语言也没用。修复：比较用 `math.isclose`；金额一律整数（分）或十进制库（decimal）。
4. **坑 4：忽略定宽整数的溢出**。现象：C/Java 里 `int` 加到上界变负数。原因：8/16/32 位是有限里程表，127+1 必然绕到 -128。排查：计数器接近类型上界时换更宽类型；Python 整数不限位数，但翻译到数据库列类型或 C 扩展时照样会溢出。
5. **坑 5：位运算与比较混用不加括号**。现象：`x & 0xFF == 10` 结果怪异。原因：`==` 优先级高于 `&`，实际算成 `x & (0xFF == 10)`。修复：位运算永远用括号圈住再比较。
6. **坑 6：len 的字符数当字节数用**。现象：按字符截断后文件/报文多出半截乱码。原因：UTF-8 变长，一个汉字 3 字节，按字节截断会腰斩编码序列。修复：解码后按字符处理，编码按字节传输，两者分清。

## 小练习

1. 手算二进制 `1101011` 的十进制值，用 `int("1101011", 2)` 验证；再把 255 和 1024 写成十六进制（提示：1024 = 4 位一组后剩下什么）。
2. 用 `-128 & 0xFF` 验证 -128 的 8 位补码是 `10000000`；再连续算 `(127+1) & 0xFF`、`(127+2) & 0xFF`，观察里程表如何绕圈，解释为什么 -128 没有对应的正数。
3. 用 `format(x, ".55f")` 逐个检查 0.5、0.125、0.2、0.3 哪些精确、哪些带误差，总结规律：什么样的十进制小数在二进制里能精确表示（提示：看分母能否写成 2 的幂）。
4. **综合排查任务**：账单系统每天累计 0.1 元费用数千笔，月底结算与银行流水差了几分钱。写一份 6 行诊断：① 用实验 4 复现误差；② 解释误差来源（IEEE 754 固有近似）；③ 对比整数「分」方案的结果；④ 说明为什么 `round()` 不能根治；⑤ 给出迁移方案（整数分或 decimal）；⑥ 说明如何写不引入新误差的单元测试（避免 float 断言）。
