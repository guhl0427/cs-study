> 一句话定义：机器里的一切信息都是 0 和 1——二进制是硬件的母语，补码让加法器顺手算负数，IEEE 754 用近似值换小数；读懂这三件事，就看懂了机器眼里的数字。

## 概念讲解

为什么是二进制？电路里最可靠的区分不是「电压多高」，而是「有没有电」：晶体管只有**导通/截止**两个稳定状态，抗干扰能力最强。要是用十个电压档直接表示十进制，信号稍抖一点就串档——所以计算机从底层就选定二进制：两个状态，非 0 即 1。

**二进制和十六进制是同一个数的两种写法**，十六进制只是二进制的缩写记法：一位十六进制正好对应 4 位二进制，读内存时人眼轻松多了。

| 十进制 | 二进制    | 十六进制 |
| ------ | --------- | -------- |
| 5      | 101       | 0x5      |
| 15     | 1111      | 0xF      |
| 10     | 1010      | 0xA      |
| 255    | 1111 1111 | 0xFF     |

位与字节：**8 bit = 1 Byte**，一个字节正好写成两位十六进制。换算直觉记一条就够：2^10 = 1024 ≈ 10^3，所以 1 KB ≈ 一千字节、1 MB ≈ 1024 KB——日常「约 1000 倍」即可，报配置时才需要分清两种进位。

**负数怎么表示？补码。** 把 8 位比特想成一个 256 格的循环里程表，转到头就绕回起点：

```text
0111 1111 =  127   ← 最大值（最高位 0：正数区）
0000 0001 =    1
0000 0000 =    0
1111 1111 =   -1   ← 最高位 1：负数区
1111 1100 =   -4
1000 0000 = -128   ← 最小值
```

正数区 0~127 占 128 个，负数区 -1~-128 也是 128 个，所以 8 位补码范围是 **-128~127**，而且不对称——-128 没有对应的 +128。妙处在于：**加法电路完全不用管符号**。负数 x 的补码等于 256 - |x|，于是「减 5」就变成「加 251」，按无符号硬加、丢掉第 9 位的进位，结果自动正确——一套加法电路通吃加减法。

**小数为什么算不准？** IEEE 754 把浮点数存成「符号 + 指数 + 尾数」，相当于二进制版的科学计数法。麻烦在于：0.5、0.25 这类 2 的负次幂能精确存，但 0.1 在二进制里是 0.0001100110011... 的无限循环——就像十进制写 1/3 = 0.333... 永远写不完，只能截断成近似值。0.1 和 0.2 各带一点误差，相加的结果恰好和 0.3 的近似值对不上，于是 `0.1 + 0.2 != 0.3`。

字符编码一句话：ASCII 用一个字节表示英文字母和符号；UTF-8 是兼容 ASCII 的变长编码——英文 1 字节、常用汉字 3 字节，它是今天互联网的通用格式。

## 代码示例

用 Python 的 `bin()` / `hex()` / `int()` 做换算实验：

```python
print(bin(202))             # 0b11001010 —— 0b 前缀表示二进制
print(hex(202))             # 0xca —— 0x 前缀表示十六进制
print(int("11001010", 2))   # 202：按二进制读字符串
print(int("ca", 16))        # 202：按十六进制读
print(0b11001010 == 0xCA == 202)   # True：同一个数的三种写法

# Python 整数没有位数限制，负数只是显示带符号；用 & 0xFF 才能看到 8 位机器里的真实比特
print(bin(-5))              # -0b101 —— 这不是补码，只是给人看的写法
a = -5 & 0xFF               # 251
print(bin(a))               # 0b11111011 —— 这才是机器里 -5 的样子
print((a + 5) & 0xFF)       # 0 —— 251+5=256，进位丢掉，正好是 -5+5=0
print((a + 2) & 0xFF)       # 253，而 253 的补码正是 -3 —— 加法电路全程没管符号
```

再验证浮点的「写不完」：

```python
print(0.1 + 0.2)            # 0.30000000000000004
print(0.1 + 0.2 == 0.3)     # False
print(format(0.1, ".55f"))  # 0.10000000000000000555111512312578270...
                            # 0.1 存进去的本来就是个近似值
```

## 常见坑

1. **坑 1：买了 1TB 硬盘只显示 931GB**。不是虚标：厂商按 1000 进位，操作系统按 1024 进位。排查：先弄清当前场合用哪种进位，2^10=1024 只是「约等于 1000」。
2. **坑 2：拿 Python 的 `bin(-5)` 理解补码**。它输出 `-0b101`，是给人看的带符号写法，不是机器里的比特。要看补码就用 `bin(-5 & 0xFF)`；n 位整数就 `& (2**n - 1)`。
3. **坑 3：浮点直接 `==` 比较、拿 float 存钱**。误差是编码固有的，换语言也没用。排查：比较用 `math.isclose(a, b)` 留容差；金额一律用整数（分）存。

## 小练习

1. 手算二进制 `1101011` 的十进制值，再用 `int("1101011", 2)` 验证；顺手把 255 和 1024 写成十六进制。
2. 用 `-128 & 0xFF` 验证 -128 的 8 位补码是 `10000000`，并解释为什么它没有对应的正数。
3. 思考题：1/3 在十进制是无限循环，0.1 在二进制也是无限循环——这两种「写不完」的共同原因是什么？什么样的十进制小数在二进制里能精确表示？
