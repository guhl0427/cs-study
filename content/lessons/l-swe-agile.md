> 一句话定义：敏捷把大需求拆成小故事和小任务，用短迭代持续交付——每次交付都跑通一个可用的闭环。

## 概念讲解

「做一个登录」不是需求，是愿望。用户故事把它补成三要素——**谁、要什么、为了什么**：

> 作为〈角色〉，我想要〈功能〉，以便〈价值〉。

价值那一栏最重要：它让讨论有靶子（这个价值值得做吗？有没有更省的路径？）。故事还必须配**验收标准**——可验证的条件，做完照着逐条勾，而不是「体验要好」这种没法勾的形容。

拿到故事后**拆任务**，粒度标准：单个任务 **2-3 天能交付**。拆不细通常说明没想清楚——拆解本身就是设计。

组织节奏的两件套：**迭代（sprint）** 是固定周期（常见两周），开始时从待办挑一批故事进本周，结束时的标准是「这批全部做完、可用」；进度贴在**看板**上三列流转：

```
| To do      | Doing        | Done        |
|------------|--------------|-------------|
| 防刷限制   | 验证码接口   | UI 稿评审   |
| 前端登录页 |              | 需求评审    |
```

Doing 列通常限流（比如每人最多 2 个）——同时干 5 件事等于一件都干不完。

**MVP 思维**：先跑通最小闭环。登录功能的 MVP 是「已注册用户能进首页」，防刷、锁定账号、记住我都是后续迭代——先有能用的 1.0，再谈 2.0。

需求变更在敏捷里是常态，但**插队要付代价**：迭代容量是固定的，加一个任务就得挤掉一个。正确姿势不是问「能不能加」，而是问「挤掉哪个」——把选择权和代价一起交给需求方。

## 代码示例

一张完整的需求卡片，从故事到拆解：

```markdown
# 用户故事：手机号验证码登录
作为 忘记密码的注册用户
我想要 用手机号收验证码登录
以便 不用记密码也能进入账号

## 验收标准
- 已注册手机号在 60 秒内收到 6 位验证码
- 验证码 5 分钟内有效
- 未注册手机号提示「号码未注册」，不发送验证码
```

拆成 2-3 天粒度的任务（估时写在后面）：

```text
验证码登录（≈1 周）
├─ 后端：发送验证码接口          (1 天)
├─ 后端：校验验证码 + 登录态     (1.5 天)
├─ 前端：登录页表单与倒计时      (1 天)
├─ 联调测试：覆盖 3 条验收标准   (0.5 天)
└─ 下一迭代：防刷与错误次数锁定
```

注意最后一行：防刷有价值，但不在 MVP 闭环里，主动挪去下个迭代——这就是「先闭环、后完善」。

## 常见坑

1. **坑 1：故事写成技术任务**。「给 user 表加一个字段」没有角色和价值，验收无从谈起。对策：先问「这对谁有什么用」，答不上来就别急着进看板。
2. **坑 2：验收标准不可验证**。「体验要好」「尽量快」没法勾。对策：写成机器或人都能判定的条件（「60 秒内收到」「输错 5 次锁定」）。
3. **坑 3：任务拆成两周一块**。进度黑箱，风险最后一刻才爆。对策：拆到 2-3 天，看板上每天都能看到列在动。

## 小练习

1. 把你手头任一想法改写成用户故事 + 3 条可验证的验收标准。
2. 给示例故事划定 MVP 版：只保留最核心的一条验收标准，其余挪到后续迭代。
3. 思考题：为什么 Doing 列限流反而让团队产出更快？（提示：切换成本）
