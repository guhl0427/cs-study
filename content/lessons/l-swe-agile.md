> 一句话定义：敏捷把大需求拆成用户故事和小任务，用短迭代持续交付——每个迭代结束都多一个能用的闭环，而不是一堆「快完成」的零件。

## 概念讲解

**「做一个登录」为什么不是需求？** 因为它三个关键问题一个都没回答，谁来都做不了。用三连问拆开看：

```text
谁用？      → 只有注册用户？还是手机号一键注册的新用户？
什么场景？  → 忘了密码走验证码？还是每次都输密码？办公室内网要不要免登？
怎样算成功？→ 60 秒内能登录成功算成功？还是防住刷接口的脚本才算成功？
```

三问问完，「登录」浮出水面的是三四个不同的故事（验证码登录、密码登录、防刷……），每个都有明确的用户和成功标准——**拆解不是把词拆碎，是把模糊的愿望变成可执行、可验收的问题**。需求评审的本质，就是当场把这三问问完。

**用户故事：三要素格式**

> 作为〈角色〉，我想要〈功能〉，以便〈价值〉。

三栏各司其职：**角色**回答「谁用」，**功能**回答「做什么」，**价值**回答「为什么值得做」。价值栏最重要：它是讨论的靶子——「以便不用记密码也能进账号」一写出来，「要不要顺便支持扫码」该不该做就有了判断依据；而「给 user 表加个字段」这类技术任务写不出价值，写不出就说明它只是某个故事里的内部步骤，不该单独成为故事。

**验收标准：可验证，Given-When-Then 一例**。「体验要好」「尽量快」没法勾；验收标准必须是做完能逐条判定的条件。行为化写法 Given-When-Then（给定-当-那么）：

```text
Given（给定）已注册手机号 138xxxx
When （当）  点击「发送验证码」
Then （那么）60 秒内收到 6 位验证码，且 5 分钟内有效
```

对照不可验证版本：「验证码发送要快、体验要好」——快是多快？好是谁说了算？Given-When-Then 把形容词换成条件；它和测试课的 Arrange-Act-Assert 三段式同构：**验收标准写得清，测试就有靶子**。

**任务拆解原则**——故事回答「什么值得做」，任务回答「怎么一步步做完」，三条硬标准：

1. **2-3 天粒度**：拆不细通常说明没想清楚——拆解本身就是设计。粒度合适，看板上每天都能看到列在动，风险不至于最后一刻才爆；
2. **有完成标志（DoD）**：「基本写完」不是完成，「测试过了 + 联调通过 + 评审合入」才是。每个任务说清「怎样算完」，避免 90% 僵局；
3. **相互独立**：任务之间不互相锁死，A 没做完 B 也能开工——串行依赖的任务链会让看板堵成一列长队。

「登录功能」完整拆解树（估时与完成标志都写上）：

```text
手机号验证码登录（≈1 周）
├─ 后端：发送验证码接口            (1 天)   完成标志：接口测试通过
├─ 后端：校验验证码 + 发登录态      (1.5 天) 完成标志：接口测试通过
├─ 前端：登录页表单与 60s 倒计时    (1 天)   完成标志：交互走查通过
├─ 联调测试：覆盖 3 条验收标准      (0.5 天) 完成标志：全绿
└─ 【下个迭代】防刷与错误次数锁定            ← 不在闭环里，主动移出
```

**迭代（sprint）与看板**。迭代是固定周期（常见两周），开始时从待办池挑一批故事进本迭代，结束的标准是「这批全部做完、可用」——宁可少放几个故事，也不留一堆 90% 的半成品。进度贴在**看板**三列流转：

```text
| To do        | Doing          | Done         |
|--------------|----------------|--------------|
| 防刷限制      | 验证码接口      | UI 稿评审     |
| 前端登录页    |                | 需求评审      |
```

**Doing 列要限流（WIP limit）**：比如每人同时在做的最多 2 个。反直觉但真实有效：同时干 5 件事，每件都在「等某个东西」的半空中，切换成本吃掉全部产出；把 WIP 压到 2，完成速度反而变快——车流慢下来不是路变窄了，是堵车散了。

**一个迭代的固定节奏**（以两周为例）：day 1 计划会——挑故事、定目标；平时——看板流转 + 每日站会（15 分钟：昨天做了什么 / 今天做什么 / 有什么障碍）；结尾——评审会演示可用成果 + 复盘会修正流程。仪式不多，全是「让信息流动」的设计。

**MVP 思维：先跑通最小闭环**。MVP（最小可行产品）不是「偷工减料版」，是「能用且完整闭环的最小集合」：

| 取舍 | 进 MVP | 挪到后续迭代 |
| ---- | ---- | ---- |
| 登录 | 已注册用户验证码登录（闭环） | 防刷、账号锁定、记住我 |
| 博客 | 写文章 + 公开可见（闭环） | 评论、草稿箱、RSS |
| 支付 | 一个支付渠道跑通 | 多渠道、优惠券、退款 |

判断口诀：**这个版本用户能不能完成核心目标**？能，就先上线拿反馈；不能，说明砍过头了。先有能用的 1.0，再谈完美的 2.0。

**需求变更：插队要问「挤掉谁」**。敏捷拥抱变更，但迭代容量是固定的——加一个任务就得挤掉一个，这不是官僚，是物理。正确姿势不是问「能不能加」，而是**问「挤掉哪个」**：列出本迭代候选清单，把选择权和代价一起交给需求方。老板听到「可以加，挤掉登录的联调还是挤掉验证码接口？」通常会自己重新掂量优先级。

## 代码示例

主线：把「做一个博客」从一句话愿望推演成 **3 个迭代 × 用户故事** 的完整计划。

**第 1 步：三连问拆愿望**：

```text
谁用？      → 一个人写、读者随便看（先不做多作者）
什么场景？  → 写技术笔记，手机上也能读
怎样算成功？→ 朋友发来链接能直接打开看完；我发一篇文章全程不超过 1 分钟
```

**第 2 步：把 MVP 定为「写 + 看」闭环**，写下三个迭代的目标：

```text
迭代 1：能写能看        ——核心闭环：内容发得出去、读得到
迭代 2：读得舒服        ——列表、按标签浏览
迭代 3：互动与传播      ——评论、分享卡片
```

**第 3 步：每个迭代写用户故事 + 验收标准**（展示迭代 1 的两张卡片）：

```markdown
# 故事 1.1：发布文章
作为 想记技术笔记的作者
我想要 在网页上写正文并点发布
以便 朋友能立刻通过链接看到它

## 验收标准
- Given 已登录作者，When 填写标题和正文后点「发布」，Then 文章页立即可访问
- Given 未登录访客，When 打开文章链接，Then 无需登录即可读全文
```

```markdown
# 故事 1.2：文章列表
作为 读者
我想要 按时间倒序看到全部文章标题
以便 找到想读的那篇

## 验收标准
- Given 已发布 5 篇文章，When 打开首页，Then 按时间倒序展示标题与日期
```

迭代 2/3 的故事同格式（此处列出标题）：

```text
迭代 2：2.1 标签分类、2.2 移动端阅读优化
迭代 3：3.1 发表评论、3.2 分享卡片、3.3 数据统计
```

**第 4 步：把迭代 1 的故事拆成任务**（2-3 天粒度、写完成标志）：

```text
故事 1.1 发布文章
├─ 后端：文章表 + 新建/查看接口       (2 天)   完成标志：接口测试通过
├─ 前端：编辑页（标题 + 正文 + 发布）  (2 天)   完成标志：能发出一篇文章
└─ 联调：发布→访问链接全链路          (0.5 天) 完成标志：验收标准逐条勾完

故事 1.2 文章列表
├─ 后端：列表接口（倒序分页）          (1 天)   完成标志：接口测试通过
└─ 前端：首页列表渲染                  (1 天)   完成标志：移动端走查通过
```

**第 5 步：排进看板**（迭代 1 中期可能长这样）：

```text
| To do           | Doing                | Done               |
|-----------------|----------------------|--------------------|
| 列表接口         | 文章表+接口 (2 天)    | 需求评审、故事拆解   |
| 首页列表渲染     | 编辑页 (2 天)        |                     |
| 联调全链路       |                      |                     |
```

WIP 检查：Doing 只有 2 个任务（限流生效）；「联调全链路」虽然排在 To do，但它依赖两个故事完成，标了依赖提醒。

**第 6 步：处理一次插队**。迭代第 5 天，产品说「加个 RSS 订阅，这周就要」：

```text
正确反应：RSS 估 2 天，本迭代剩余容量 0 → 挤掉谁？
候选 A：联调全链路（挤掉 = 闭环验不了，不建议）
候选 B：首页列表渲染（挤掉 = 迭代 1 交付打折）
→ 决策交还：要么 RSS 进下迭代，要么明确挤掉 B 并承担后果
```

**第 7 步：迭代复盘**。迭代结束逐条勾验收标准：故事 1.1 全过、故事 1.2 因挤队顺延——**这个迭代的产出是「一个能发布、能访问的博客」**，而不是「两张 90% 的卡片」。下迭代开始前把顺延故事重新排序。

**第 8 步：最终计划全景**（给需求方的一页纸）：

| 迭代 | 目标 | 故事 | 交付闭环 |
| ---- | ---- | ---- | ---- |
| 1 | 能写能看 | 1.1 发布文章、1.2 文章列表 | 发得出去、读得到 |
| 2 | 读得舒服 | 2.1 标签分类、2.2 移动端优化 | 找得到、读得爽 |
| 3 | 互动传播 | 3.1 评论、3.2 分享卡片、3.3 数据统计 | 有反馈、传得开 |

## 常见坑

1. **坑 1：故事写成技术任务**。「给 user 表加一个字段」没有角色和价值，验收无从谈起。排查：故事写不出「以便…」就是信号。对策：先问这对谁有什么用，答不上来就降级为某个故事下的任务。
2. **坑 2：验收标准不可验证**。「体验要好」「尽量快」没法勾，验收时变成吵架。对策：Given-When-Then 或可数条件（「60 秒内收到」「输错 5 次锁定」）。
3. **坑 3：任务拆成两周一块**。进度黑箱，风险最后一刻才爆。排查信号：看板 Done 列连续几天不动。对策：拆到 2-3 天，每天都能看到列在动。
4. **坑 4：Doing 列不限流**。人人同时抱 4 个任务，产出反而最慢。对策：给 Doing 设 WIP 上限（如每人 2 个），新任务想进来，先完成旧的。
5. **坑 5：MVP 砍过头或砍不动**。砍过头 = 闭环不成立（支付 MVP 只做了下单没做支付）；砍不动 = 什么都想塞，三个月不见 1.0。对策：回到口诀——用户能否完成核心目标。
6. **坑 6：把「敏捷」理解成「随时改需求」**。迭代中无限制插队，团队永远在救火。对策：变更可以进，但必须走「挤掉谁」的等价交换。

## 小练习

1. 把你手头任一想法先过三连问，再改写成用户故事 + 3 条可验证的验收标准（至少一条用 Given-When-Then）。
2. 给示例「验证码登录」故事划定 MVP 版：只保留最核心的一条验收标准，其余挪到后续迭代，并说明砍掉了谁、为什么闭环还成立。
3. 综合任务：模仿主线，把「做一个记账本」推演成 2 个迭代 × 每迭代 2 个用户故事（含验收标准），并把迭代 1 拆成 2-3 天粒度的任务树。
4. 思考题：为什么 Doing 列限流反而让团队产出更快？试着用「切换成本」和「半成品」两个词，解释给非技术同事听。
