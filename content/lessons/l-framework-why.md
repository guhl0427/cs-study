> 一句话定义：前端框架解决的核心问题只有一个——**数据变了，页面怎么跟着变**；它把「手动同步 DOM」升级为「声明式描述 + 自动同步」，并用组件化让代码可复用。

## 概念讲解

**从三件套课程的痛点说起。** DOM 课的待办应用里，每次数据变化你都要手动调 `render()`；事件课里你要小心「监听别重复绑」。数据一多、交互一复杂，会暴露两类失控：

1. **同步散弹**：一个数据可能在 5 处显示（列表、计数、汇总、徽章、标题），改数据后要记得手动更新 5 处——漏一处就是 bug，而且这类 bug 不报错、只是显示错；
2. **状态与 DOM 双写**：真实状态存在数据里，但页面上的 class、文本也可能被你直接改过——两份「真相」渐渐不一致，没人说得清页面当前到底是什么状态。

**先算一笔账：手动同步的成本是怎么失控的。** 设页面有 S 个状态、每个状态平均在 D 处显示、每个状态平均有 E 个修改入口（能改它的按钮/表单）：

- **每加一个显示点的成本**：原生版要补 1 行 `querySelector` + 1 行赋值，约 2 行同步代码；而且这些同步散落在**所有修改入口**里——同一个数据被 3 个按钮改，3 处都要写；
- **必须写对的同步点总数 = S × E × D**：小例子 5 状态 × 2 入口 × 2 显示点 = 20 处；真实项目 50 状态 × 3 入口 × 平均 6 显示点 = 900 处——「人肉记住 900 个位置」就是失控的定义；
- **bug 概率推演**：假设你每处记得同步的把握有 95%，20 处全对的概率是 0.95²⁰ ≈ 36%；900 处全对的概率约等于 0——**漏同步不是「会不会」，是「今天漏几处」**。更糟的是这类 bug 静默：不报错、只显示错，控制台干干净净。

框架要消灭的正是这个乘法：把「记住所有同步点」换成「声明显示点」一次，修改入口随便加。

**框架的答案：声明式 UI（UI = f(state)）**。你不再写「怎么改页面」，只声明「页面长什么样是这个状态的函数」——状态一变，框架自动算出 DOM 要怎么改：

```text
手写：数据变 → 你写代码找到 DOM → 手动改 N 处（会漏）
框架：数据变 → 框架重新计算 UI 描述 → 自动 diff 出最小改动 → 应用到 DOM（不漏）
```

React 与 Vue 只是「声明式」的两条实现路径（React 重跑组件函数再 diff，Vue 靠响应式追踪依赖精准更新——框架深入课展开），世界观一致。

**为什么「重新算一遍再 diff」是划算的设计？** 直觉上「每次全量重算」很浪费，但这笔账要按阶段分层算：

| 阶段 | 成本 | 原因 |
| ---- | ---- | ---- |
| 重新生成 UI 描述（虚拟 DOM） | 便宜 | 只是跑一段 JS 生成普通对象树，纯内存操作 |
| 前后两棵树 diff | 便宜 | 对象树对比，同样是内存计算，毫秒级 |
| 把差异写进真实 DOM | 昂贵 | 每次改动都可能触发浏览器重排（layout）与重绘（paint） |

设计结论：**把最昂贵的「真实 DOM 操作」压缩到最小次数与最小面积**，代价是把便宜的事（JS 计算）多做一遍。这是所有声明式框架共享的底层经济学，也是「虚拟 DOM」三个字真正解决的问题——不是「比 DOM 快」，而是「让你不用手写 DOM 操作，还能只做必要的那几次」。

**第二个支柱：组件化。** 把页面拆成独立小单元（每个 = 结构 + 逻辑 + 样式），组件像乐高一样拼装复用：

```text
页面 = <Header/> + <TodoList/> + <TodoItem/>×N + <Footer/>
TodoItem 在列表里写一次，渲染一百次；改它一处，一百处生效
```

组件还带来**命名空间式的隔离**——每个组件管自己那块页面，状态放哪、谁负责更新，边界清晰。

**复用与隔离是组件化的双重收益**，同一套机制的两个视角：

| 维度 | 复用（对外供给） | 隔离（对内防御） |
| ---- | ---- | ---- |
| 收益 | 写一次、用 N 处；改一处全局生效 | 改这里不会炸那里；故障锁定在一个小单元 |
| 机制 | props 传参、组件组合拼装 | 单向数据流、scoped 样式、清晰的 props 边界 |
| 类比 | 乐高积木的「量产同一块」 | 积木之间的「卡扣」保证拼不乱 |
| 反面 | 无组件化：复制粘贴一百份 li，改样式要改一百处 | 无隔离：全局变量满天飞，改一行全页联动 |

**框架的分层地图**——学框架前先知道「框架到底是什么东西」：

```text
┌──────────────────────────────────────────────────────┐
│ 应用层：你的业务组件（TodoList、购物车、表单…）        │ ← 你每天写的
├──────────────────────────────────────────────────────┤
│ 生态层：路由（页面间跳转）· 全局状态（数据放哪）        │ ← 深入课两大件
│         组件库（现成 UI）· 请求库（网络数据）           │
├──────────────────────────────────────────────────────┤
│ 框架核心：响应式系统（数据变 → 找到依赖它的组件）        │ ← 本课开始理解
│           虚拟 DOM + diff（算出最小 DOM 改动）          │
│           组件调度（挂载/更新/卸载的生命周期）           │
├──────────────────────────────────────────────────────┤
│ 底层平台：真实的 DOM API 与事件系统（三件套的内容）      │ ← 永远是地基
└──────────────────────────────────────────────────────┘
```

读图结论：框架 = **核心层包揽「数据→视图同步」的苦活 + 生态层解决核心不管的工程问题**（页面间怎么跳、跨页数据放哪）。你今后的学习路线正好对应这张图：入门学应用层语法 → 深入学核心层原理与生态层两大件 → 底层平台永远要懂（调试时绕不开它）。

**MVC / MVVM 一句话**：它们是「界面、数据、逻辑怎么分工」的经典分层词汇——MVC 把代码分成 Model（数据）、View（显示）、Controller（粘合层）；MVVM 把粘合层换成 ViewModel，强调「数据 ↔ 视图」自动绑定。Vue 官方如今更愿意自称「响应式 + 声明式」，不必纠结归哪一类——**记住分工思想即可：显示与数据分离，中间有明确的粘合层，框架把粘合自动化了**。

**框架不是必需品**：页面交互极简（几个静态页）用原生 JS 更轻；一旦「同一数据多处显示 + 频繁交互 + 需要复用 UI」，框架的收益就压倒成本。判断标准：**手动同步 DOM 的代码是否已经开始重复**。

## 代码示例

主线：同一个「计数器 + 历史记录」小应用，原生 JS 与 Vue 各写一遍，亲眼对比：

**版本 1：原生 JS（三件套的姿势）**：

```html
<div>
  <button id="plus">+1</button>
  <p>当前：<span id="count">0</span></p>
  <p>历史：<span id="history">[]</span></p>
</div>
<script>
  let count = 0
  const history = []

  document.querySelector("#plus").addEventListener("click", () => {
    count += 1
    history.push(count)
    // ⚠️ 手动同步：每个显示数据的地方都要记得改——漏一处就 bug
    document.querySelector("#count").textContent = count
    document.querySelector("#history").textContent = JSON.stringify(history)
  })
</script>
```

**版本 2：Vue 3（同一需求）**：

```vue
<script setup>
import { ref } from 'vue'
const count = ref(0)
const history = ref([])
</script>

<template>
  <button @click="plus">+1</button>
  <p>当前：{{ count }}</p>
  <p>历史：{{ history }}</p>
</template>

<script>
// 上面模板里的 plus：
// function plus() { count.value += 1; history.value.push(count.value) }
// 没有 querySelector，没有手动同步——数据变了，两处显示自动更新
</script>
```

差异一目了然：**原生版每加一个显示位置就要加一行手动同步代码；Vue 版模板只是「声明显示什么」，加显示位置零额外成本**。这个示例只有 1 个状态、2 处显示——真实项目里是 50 个状态、300 处显示，手动同步直接失控。

**分支任务：给两个版本同时加「双倍模式」**——新需求：页面显示「双倍值 = 当前值 × 2」，再加一个「清空历史」按钮。先猜两边各要改几处，再动手对照：

原生版加需求（数一数你写了多少同步行）：

```html
<!-- 新增两个显示点 -->
<p>双倍：<span id="double">0</span></p>
<button id="clear">清空历史</button>
```

```js
// plus 的回调里要补 1 行同步：
document.querySelector("#double").textContent = count * 2
// clear 是新的修改入口，又要把受影响的显示全部同步一遍：
document.querySelector("#clear").addEventListener("click", () => {
  history.length = 0
  document.querySelector("#history").textContent = JSON.stringify(history)
  document.querySelector("#double").textContent = count * 2
})
```

Vue 版加需求（只声明，不同步）：

```vue
<script setup>
import { ref, computed } from 'vue'
const count = ref(0)
const history = ref([])
const double = computed(() => count.value * 2)   // 派生值：永远自动跟随 count
function clearHistory() { history.value = [] }   // 只改数据，页面自己会变
</script>

<template>
  <button @click="plus">+1</button>
  <p>当前：{{ count }}</p>
  <p>双倍：{{ double }}</p>
  <p>历史：{{ history }}</p>
  <button @click="clearHistory">清空历史</button>
</template>
```

对比结论：同样的需求，原生版要**在每个修改入口**补同步代码（clear 按钮就是新入口，同步逻辑重写一遍），漏一处就是静默显示 bug；Vue 版只是**多声明了一行显示**。需求继续增长时差距是乘法级的——这就是前面那笔「同步成本账」从纸面落到代码的样子。

## 常见坑

1. **坑 1：把「学框架」当成「背语法」**。框架语法只占 20%，剩下 80% 是组件化思维（怎么拆组件、状态放哪、父子怎么通信）——语法三天，思维三个月。
2. **坑 2：三件套不牢就上框架**。分不清「框架的功劳」和「JS 本身的能力」——出了问题不知道该查框架还是查 JS。先用原生写过待办应用（三件套课的主线），再学框架。
3. **坑 3：框架全能论**。框架管「数据→视图」同步，不管请求设计、不管 CSS 架构、不管业务逻辑分层——那些是软件工程课的内容。
4. **坑 4：在小项目里硬上框架**。三个静态页引 Vue + 构建工具是负收益——框架的成本（学习/构建链/包体积）要靠交互复杂度赚回来。
5. **坑 5：声明式界面里混入手动 DOM 操作**。现象：用了 Vue 还在事件回调里写 `document.querySelector(...).textContent = ...`，页面偶尔「改不动」或显示被莫名还原。原因：框架维护的 UI 描述与你手改的真实 DOM 互相打架——下次框架更新时，可能把你手改的内容覆盖回去，两套「真相」又回来了。排查：全局搜索 `querySelector` / `getElementById`，出现即说明同一份数据有两条修改路径；删掉手改那条，回归「只改数据」。
6. **坑 6：以为「有了框架就不用懂 DOM」**。现象：布局错位、事件冒泡异常时束手无策，只能整个组件推倒重写。原因：框架最终输出的仍是真实 DOM 与浏览器事件——虚拟 DOM 只是中间描述，最终必然落到 DOM。对策：三件套的 DOM/事件知识是调试框架应用的「X 光片」：遇到诡异渲染问题，F12 看真实 DOM 的实际结构与 class，往往一眼定位。

## 小练习

1. 跑通两个版本的计数器，然后给两个版本同时加一个需求：「点击按钮时按钮要禁用 0.5 秒防连点」——观察哪个版本改起来更分散。
2. 在 TodoMVC 上找 Vue 和 React 两个实现，对照它们的源码结构（入口/组件划分/状态放哪），写下三点异同。
3. 综合任务：给原生版计数器再加两个状态（步长、步长历史），体验手动同步的扩散成本，并记录你加了几行「同步代码」；随后用主线分支任务的 Vue 版做同样的扩展，对比两边行数与遗漏风险。
4. 思考题：为什么说「框架把复杂度从代码里转移到了框架内部」？这个交换什么时候划算？（提示：对照分层地图——复杂度没有消失，只是被压缩进了你不用天天碰的核心层。）
