> 一句话定义：分层 = 把「从敲下回车到看到网页」这件事拆成几段，每段只解决一个问题，段与段之间靠约定（协议）衔接——理解了分层，你就拿到了一张「网络出事该从哪查起」的地图。

## 概念讲解

### 为什么一定要分层？

打开一个网页，背后同时发生着很多件事：查地址、建连接、选路、纠错、编码、渲染……如果不分层，任何一个环节出问题，都要把整个系统翻个底朝天。分层的本质是**关注点分离**——和你写代码时的模块化完全同构：函数只管自己的逻辑，靠参数和返回值衔接；网络层与层之间靠**协议**衔接，靠**封装**传递数据。

分层还有第二个好处：**每层可以独立升级**。你把 Wi-Fi 换成插网线，网页代码一行不用改；HTTP 从 1.1 升级到 2，下面的 IP 层毫不知情。就像快递公司换了车型，寄件人只管写地址——底层怎么运输，是运输公司的事。

### 先走一遍全流程：输入 URL 到看到页面

你在浏览器敲下 `https://github.com` 回车。这一秒之内，四层完成了一次接力：

1. **应用层（DNS）**：浏览器不知道 github.com 是哪台机器，先去问 DNS「它的 IP 是多少」（DNS 本身也是应用层协议，下一课细讲）；
2. **传输层（TCP）**：拿到 IP 后，浏览器与服务器的 443 端口建立 TCP 连接（三次握手，传输层那一课细讲）；
3. **网络层（IP）**：握手的每一个包，交给 IP 协议，一站一站路由过去；
4. **接口层**：每一站之间，由以太网/Wi-Fi 把比特真正送到对面；
5. 连接建立后，浏览器把 HTTP 请求发出去，服务器原路把 HTML 送回来；
6. **应用层（HTTP）**：浏览器解析 HTML、加载 CSS/JS、渲染——你看到了页面。

注意一个关键直觉：**上层的「一段话」，到了下层就成了一件「货物」**。浏览器写好的 HTTP 报文，在传输层眼里只是要保价运输的包裹，它不关心内容；在网络层眼里连包裹都只是要选路的箱子。

### OSI 七层 vs TCP/IP 四层：为什么实际只讲四层

教科书常背 OSI 七层，工程实践用 TCP/IP 四层。两者是对同一件事的两种切法：

| OSI 七层 | TCP/IP 四层 | 这层解决什么 | 代表协议/设备 |
| ---- | ---- | ---- | ---- |
| 7 应用层 | 应用层 | 发什么内容、和谁对话 | HTTP、DNS、WebSocket |
| 6 表示层 | ↘（合并进应用层） | 编码、压缩、加密 | TLS 加密（常划入此处） |
| 5 会话层 | ↗ | 会话的建立与维持 | 实际由应用自己处理 |
| 4 传输层 | 传输层 | 进程到进程、丢不丢 | TCP、UDP、端口 |
| 3 网络层 | 网络层 | 主机到主机、怎么走 | IP、ICMP（ping）、路由器 |
| 2 数据链路层 | 网络接口层 | 相邻两台设备怎么传 | 以太网、Wi-Fi、交换机 |
| 1 物理层 | ↗ | 比特怎么变成电/光信号 | 网线、光纤、网卡 |

为什么实际只讲四层？因为 OSI 是 ISO 制定的**理论参考模型**，其中 5/6/7 三层在实际协议里几乎总是揉在一起、由应用自己处理（比如 HTTP 自己管编码，HTTPS 自己管加密）；而 4/3/2/1 这四段在真实世界里边界清清楚楚、各自都有代表性协议。**背四层能干活，背七层只能背书**——但面试问起，你要知道四层里的应用层 ≈ 七层里的 5+6+7。

### 每层职责与快递类比

把「寄快递」映射到四层，职责一下就清楚了：

| TCP/IP 层 | 一句话职责 | 快递类比 | 排错时对应什么 |
| ---- | ---- | ---- | ---- |
| 应用层 | 内容说了什么、给谁看 | 信的内容与格式 | 服务返回 200 还是 500 |
| 传输层 | 货送到「哪扇门」、丢不丢 | 快递单：门牌号 + 保价方式 | 端口通不通 |
| 网络层 | 从哪条干线走、怎么选路 | 干线运输路线规划 | ping 得通吗 |
| 网络接口层 | 最后一段路的实际搬运 | 配送员的电动车 | 网线插了吗、Wi-Fi 连了吗 |

### 封装与解封装：数据怎么「穿上外套」

发送方自顶向下**逐层封装**，接收方自底向上**逐层解封装**：

```text
发送方（封装 = 套娃打包）                接收方（解封装 = 逐层拆包）

 应用层  [ HTTP 报文 ]                    [ HTTP 报文 ]        ← 浏览器拆出内容
             │ 信纸装进信封                    ↑
 传输层  [TCP头 | HTTP报文]               [TCP头 | HTTP报文]   ← 核对序号、确认收货
             │ 信封贴上快递单（端口）          ↑
 网络层  [IP头 | TCP头 | HTTP报文]        [IP头 | TCP头 | ...] ← 看地址，决定下一站
             │ 包裹贴上干线标签（IP）          ↑
 接口层  [帧头|IP头|TCP头|HTTP报文|帧尾]  ← 网卡拆掉帧，把内层上交
             ↓ 通过网线/Wi-Fi 发出比特 ───→ 对面网卡收到比特
```

每一层的「头」就是该层的管理信息：TCP 头写着端口号和序号，IP 头写着源地址和目标地址。接收方每层只读自己的头、剥掉它，把剩下的交给上层——**这就是为什么两层协议可以互不知晓地协同**。

### 分层给排错的礼物：自底向上逐层收窄

分层最大的实用价值是：**断点只可能落在某一层，而各层都能单独验证**。于是有了经典排查顺序——从物理层往应用层走，每一步排除一片嫌疑：

```text
① 接口层  网线插了吗？Wi-Fi 连了吗？拿到 IP 了吗？   → ipconfig / ifconfig
② 网络层  能 ping 通网关？能 ping 通目标 IP？        → ping
③ 传输层  目标端口（80/443）开得开吗？               → curl -v telnet://host:port
④ 应用层  服务到底返回了什么（200/404/500）？        → curl -sI
```

为什么自底向上？因为底层是上层的前提：连 IP 都不通，应用层任何检查都是空转。每一步都把嫌疑范围砍掉一半，三四步之内必然定位——这就是「网页打不开怎么排查」这道面试题的标准答案框架。

## 代码示例

主线任务：给一台机器做**四层体检**，并完整推演「网页打不开」的排查剧本。全程约 20 分钟，命令在 Windows 的 PowerShell/Git Bash、macOS/Linux 终端都可运行（个别命令平台不同，均已标注）。

### 第 0 步：把命令和层对应起来

| 层 | 检查命令 | 看什么 |
| ---- | ---- | ---- |
| 接口层 | `ipconfig`（Win）/ `ifconfig`（Mac/Linux） | 拿到 IP 和网关了吗 |
| 网络层 | `ping 目标` | 有回复、耗时多少 |
| 传输层 | `curl -v telnet://主机:端口` | 有没有 Connected |
| 应用层 | `curl -sI https://主机` | 返回什么状态码 |

### 第 1 步：接口层体检——我真的连上网了吗？

```bash
ipconfig        # Windows；macOS/Linux 用 ifconfig 或 ip addr
```

预期输出（Windows 节选）：

```text
无线局域网适配器 WLAN:
   IPv4 地址 . . . . . . . . : 192.168.1.103
   默认网关 . . . . . . . . : 192.168.1.1
```

输出说明了什么：拿到 `192.168.x.x` 这样的私网地址，说明 DHCP 正常、Wi-Fi 已连上；默认网关就是你家路由器的门牌号。如果适配器显示「媒体已断开连接」或根本没有 IPv4 地址，问题在最底层——查网线、Wi-Fi 开关、路由器。

再验证到路由器这最后一公里：

```bash
ping 192.168.1.1     # 换成你上面看到的「默认网关」地址
```

预期输出（节选）：`来自 192.168.1.1 的回复: 字节=32 时间<1ms TTL=64`。有回复 = 你到路由器这段是通的。不通 = 你的设备与路由器之间断了（重连 Wi-Fi、换插口）。

### 第 2 步：网络层体检——能走到目标主机吗？

```bash
ping www.baidu.com
```

预期输出（Windows 节选）：

```text
正在 Ping www.baidu.com [110.242.68.4] 具有 32 字节的数据:
来自 110.242.68.4 的回复: 字节=32 时间=12ms TTL=52
```

这一条输出里有三个信息，逐一判读：

1. **方括号里的 IP**——域名解析成功了，说明 DNS 至少没坏（解析失败会显示「未知主机」，那是 DNS 问题，不是断网）；
2. **「来自 xxx 的回复」**——ICMP 包走到了对面又走了回来，路由可达；
3. **时间=12ms**——链路质量。数字巨大或丢包，说明网络拥堵或线路差。

### 第 3 步：传输层体检——目标端口开得开吗？

ping 只证明「主机可达」，不证明「服务开门」。传输层用这条命令：

```bash
curl -v telnet://www.baidu.com:443
```

预期输出（节选）：

```text
* Trying 110.242.68.4:443...
* Connected to www.baidu.com (110.242.68.4) port 443
```

看到 `Connected` = TCP 三次握手成功 = 443 端口开着、有进程在监听。**之后光标停住不动是正常的**——telnet 模式在等数据交换，按 `Ctrl+C` 退出即可。

再做一个对照实验，体验「端口不通」长什么样：

```bash
curl -v --max-time 5 telnet://www.baidu.com:81
```

预期输出：`Connection timed out` 或 `Failed to connect`。同一个 IP，ping 得通，端口却进不去——这就是「ping 通 ≠ 网络没问题」的铁证：挡住你的不是网线，是防火墙或没开的服务。

### 第 4 步：应用层体检——服务到底回了什么？

```bash
curl -sI https://www.baidu.com
```

预期输出（节选）：

```text
HTTP/2 200
server: BWS/1.1
content-type: text/html
```

`HTTP/2 200` 说明应用层服务正常工作；`-I` 只取响应头，速度快、输出干净。如果是 5xx，线索就该移交给服务端同学了——前面三层都没错，错在「内容的生产者」。

### 第 5 步：完整剧本——「网页打不开」排查演练

同事喊：「网站打不开了！」别急着重启路由器，按地图从下往上走一遍。把下面五条命令按顺序执行（对象换成你怀疑的域名）：

```bash
ipconfig                             # ① 接口层：拿到 IP 和网关了吗
ping 192.168.1.1                     # ② 接口层：到路由器通吗
ping 110.242.68.4                    # ③ 网络层：绕过域名，直接 ping 一个已知 IP
ping www.baidu.com                   # ④ DNS + 网络层：域名能解析吗
curl -v telnet://www.baidu.com:443   # ⑤ 传输层：端口开吗
curl -sI https://www.baidu.com       # ⑥ 应用层：服务回什么
```

六个结果组合起来，对照这张判例表，三四步内必然收窄到一层：

| 现象组合 | 结论 | 谁来修 |
| ---- | ---- | ---- |
| ①就失败 / ping 网关都不通 | 你本地断网了 | 查 Wi-Fi、网线、路由器 |
| ②通、③通、④「未知主机」 | DNS 坏了，不是断网 | 换 DNS 服务器（DNS 课细讲） |
| ④通、⑤端口连不上 | 防火墙/端口/代理问题 | 查安全组、VPN、代理设置 |
| ⑤通、⑥是 5xx | 应用层故障 | 找服务端，报上状态码 |

这套顺序的价值不是「知识」，而是**纪律**：按层走，每步砍掉一半嫌疑；乱试，只能靠运气。

## 常见坑

1. **坑 1：ping 通就宣布「网络没问题」**。现象：ping 正常，网页就是打不开。原因：ping 只验证网络层，443 端口被防火墙挡住时页面照样连不上。排查：补一条 `curl -v telnet://目标:443` 看有没有 Connected。
2. **坑 2：telnet:// 连上后以为程序卡死**。现象：`Connected` 之后终端毫无动静。原因：telnet 模式连上后就在等数据，本来就「不动」。排查：这恰恰是成功的表现，按 `Ctrl+C` 退出；加 `--max-time 5` 防止干等。
3. **坑 3：把 DNS 故障当成断网**。现象：`ping www.xxx.com` 显示「无法解析主机」，就断定没网。原因：域名解析失败 ≠ 链路不通。排查：直接 `ping 110.242.68.4`（一个已知 IP），IP 通而域名不通，锅在 DNS。
4. **坑 4：死背 OSI 七层，说不出每层职责**。现象：面试能背七层名，追问「传输层解决什么」就哑火。原因：把分层当名词表背。对策：每个层用一句话答「它解决什么问题 + 代表协议 + 类比什么」，答不出就重背。
5. **坑 5：以为分层是物理上的分开**。现象：追问「四层是不是四台设备」。原因：四层都跑在同一台机器、同一块网卡上，分层是**逻辑**分工，靠封装衔接。路由器工作在网络层、交换机在接口层，那是设备视角，不是分层视角。
6. **坑 6：遇到打不开就重启路由器碰运气**。现象：重启后有时好有时坏，不知道为什么。原因：没有收窄范围，碰巧撞上。对策：永远按「接口层 → 网络层 → 传输层 → 应用层」走一遍，让证据告诉你哪层断了。

## 小练习

1. 挑三个你常用的网站，各跑一遍第 1–4 步体检命令，把「每层通了/不通 + 关键数字（IP、延迟、状态码）」记进一张表格。
2. 故意断开 Wi-Fi，重跑第 1 步和第 2 步，观察失败输出长什么样（「媒体已断开」「传输失败」）——下次见到同样输出，你能秒判是哪一层断了。
3. 用寄快递的类比，向一位不懂网络的朋友讲清楚：为什么收到的数据要一层层「拆包」，而不是直接把比特倒给浏览器？
4. **综合排查任务**：找一个你确实打不开的网站（公司内网、被墙的站点、挂掉的服务均可），把第 5 步剧本完整走一遍，写一份 5 行以内的诊断结论：断在哪一层、证据是哪条命令的哪行输出、该找谁修。
