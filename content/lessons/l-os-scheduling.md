> 一句话定义：调度器是 CPU 时间的**时间片分配员**——几十个进程抢几个核，靠高速切换制造「并行」错觉；切换会切开「读-改-写」，这正是竞态、死锁、饥饿三大并发问题的总根因。

## 概念讲解

![时间片轮转调度的时间线](fig:os-scheduling)

### 调度器：操场上唯一的球

类比：操场只有一个篮球（每个 CPU 核），几十个班都想打。体育老师（调度器）的办法是**时间片轮转**：每班发 10 分钟，到点换人，循环往复——谁也不许霸场。如果校队今天要训练，老师会给他们**插队加场**——这就是**优先级调度**。真实操作系统是两者的混合体：交互任务（你正在敲字的窗口）优先级高，后台任务（定时备份）优先级低，Linux 的 CFS、Windows 的抢占式调度名号不同，骨架都是这套。

时间片多长是个两难：太长，你打字时系统在让备份程序跑，窗口卡顿；太短，换人本身（上下文切换）把时间耗光。折中结果通常在几毫秒量级。

### 上下文切换：每次换人都付的账

把 A 换成 B 不是免费的：调度器要保存 A 的寄存器快照进它的 PCB → 换上 B 的页表（进程切换才需要，线程切换跳过这步）→ 装入 B 的寄存器 → CPU 缓存里 A 的热数据对 B 大半失效。直接成本是微秒级，间接成本（缓存冷启动）更疼。

```text
CPU 时间轴 ──────────────────────────────────────────────→
 │ A │ A │ A │ B │ B │ B │ A │ A │ B │ ...   ← 每格几毫秒
       ↑ 切换点：保存 A 上下文、恢复 B 上下文（微秒级纯开销）
```

记住这个形状，后面用 `vmstat` 的 cs 列就能亲眼看它一秒发生几千次。

### 竞态条件：切换切开「读-改-写」

`counter += 1` 在机器层面不是一步，而是三步：**读内存 → 加 1 → 写回**。线程可以在任意两步之间被切走：

```text
时间 →     ①读 5    ②+1=6              ④写回 6
线程 A：   ──────────────────────────────────────
线程 B：             ①读 5   ②+1=6  ③写回 6
                            ↑ A 还没写回，B 读到的还是 5
结果：两次 += 1，计数只涨了 1 —— 一次「丢失更新」
```

凡结果取决于线程交错顺序的代码，就叫**竞态条件（race condition）**。它的可怕在于偶现性：交错是随机的，所以 bug 一万次里才出一次，日志干净、复现全凭运气——理解切换时机，才算真正看懂了这类 bug 的成因。

### 死锁：四个条件与「按序加锁」

死锁的经典画面：两个银行家各攥着一笔贷款不放，又都等着对方先放款才能成交——谁也不动，永远。教科书总结死锁需要**四个条件同时成立**：

| 条件 | 含义 | 工程上的破法 |
| ---- | ---- | ---- |
| 互斥 | 锁一次只给一个人 | 用无锁结构/原子操作替代锁 |
| 持有并等待 | 拿着 A 还伸手要 B | 一次性申请全部，要不到就全放 |
| 不可抢占 | 别人不能抢走你的锁 | try_lock 超时放弃、退避重试 |
| 循环等待 | A 等 B、B 等 A，绕成圈 | **全局固定加锁顺序**（最实用） |

前三个条件多数场景下改不起（要的就是互斥），工程上真正常用的是**打破循环等待**：全项目约定一个加锁顺序（比如「先锁编号小的账户」），所有人都遵守，环路就永远绕不起来。

```text
不安全：A 攥着锁 1 等锁 2，B 攥着锁 2 等锁 1 → 对峙卡死
安全：  A 拿到锁 1 后去等锁 2；B 也得先拿锁 1 → 排在 A 后面，A 走完 B 才开始
```

### 饥饿：系统在转，但有人永远轮不上

死锁卡死所有人；饥饿只饿死一个：调度器层面，低优先级任务被源源不断的高优先级任务插队，永远排不上（医院里 VIP 一直插队，普通号永远叫不到）；锁层面，锁不保证公平，手快者反复得手。经典解法是**老化（aging）**：等得越久优先级越高，确保人人有份。饥饿最难发现——监控看系统一切正常，只有那个倒霉用户的请求一直超时。

### 三大问题对照小结

| 问题 | 现象 | 根因 | 典型解法 |
| ---- | ---- | ---- | ---- |
| 竞态 | 数据偶现不对（通常偏小/错乱） | 复合操作被切换切开 | 互斥锁、原子操作 |
| 死锁 | 一组线程整体卡死，CPU 空转 | 循环等待 | 全局固定加锁顺序 |
| 饥饿 | 某任务长期得不到执行 | 无限插队/不公平 | 老化、公平锁 |

为什么这是后端必修课？服务端天然多线程/多协程，计数错、缓存脏、偶现卡死这类「跑一万次才出一次」的 bug，几乎全是这三个问题的化身。看不懂调度，就只能靠重启玄学。

## 代码示例

主线任务：实测竞态 → 加锁修复对照 → 复现死锁再救活 → 数机器的切换频率。全程约 25 分钟。

### 实验 1：亲眼看竞态——双线程无锁自增

```python
# demo_race.py
import threading

counter = 0
N = 100_000

def add_n():
    global counter
    for _ in range(N):
        counter += 1        # 读→改→写，中途可能被切走

for run in range(5):        # 跑 5 次，看结果的波动
    counter = 0
    ts = [threading.Thread(target=add_n) for _ in range(2)]
    for t in ts: t.start()
    for t in ts: t.join()
    print(f"第 {run + 1} 次: {counter}（期望 {2 * N}）")
```

预期输出（数字每次都不一样，这是重点）：

```text
第 1 次: 148311（期望 200000）
第 2 次: 121907（期望 200000）
第 3 次: 166245（期望 200000）
第 4 次: 133580（期望 200000）
第 5 次: 158392（期望 200000）
```

输出说明了什么：每次都小于期望值且波动——丢失更新量取决于线程恰好在哪里交错，本质是随机的。把 `N` 改成 1000 再跑，结果多半「看起来正常」：交错概率没变，但丢失比例小到看不见——这正是竞态 bug 在测试环境神出鬼没的原因。

### 实验 2：一把锁修好它（对照）

```python
# demo_lock.py
import threading, time

counter = 0
lock = threading.Lock()
N = 100_000

def add_n():
    global counter
    for _ in range(N):
        with lock:          # with 块结束自动释放，忘不掉、异常跑不掉
            counter += 1

t0 = time.perf_counter()
ts = [threading.Thread(target=add_n) for _ in range(2)]
for t in ts: t.start()
for t in ts: t.join()
elapsed = time.perf_counter() - t0
print(f"结果 {counter}（期望 200000），耗时 {elapsed:.3f}s")
```

预期输出：

```text
结果 200000（期望 200000），耗时 0.089s
```

输出说明了什么：锁把「读-改-写」三步圈成一个不可分割的整体，谁拿到锁谁做完，别人在门口排队——正确性有了，代价是 200000 次自增被彻底串行化（对比无锁版耗时能看出锁的开销）。**锁是用性能换正确性，所以锁内代码要尽量短——别把网络请求塞进锁里。**

### 实验 3：复现死锁，再按序加锁救活

```python
# demo_deadlock.py
import threading, time

lock1, lock2 = threading.Lock(), threading.Lock()

def worker_a():
    with lock1:
        time.sleep(0.1)      # 故意停一拍：给对方时间拿到另一把锁
        with lock2:
            print("A 拿到两把锁")

def worker_b():              # 加锁顺序与 A 相反 —— 死锁配方
    with lock2:
        time.sleep(0.1)
        with lock1:
            print("B 拿到两把锁")

t1 = threading.Thread(target=worker_a)
t2 = threading.Thread(target=worker_b)
t1.start(); t2.start()
t1.join();  t2.join()
print("main 正常结束")        # ← 永远走不到这一行
```

预期输出：**什么都没有**——程序挂起，只能 Ctrl+C。输出说明了什么：A 攥着 lock1 等 lock2，B 攥着 lock2 等 lock1，循环等待成立，四条件凑齐，谁也不让谁。修复只要一行：把 `worker_b` 里的两把锁顺序对调成「先 lock1 后 lock2」，与 A 一致——再跑，两行输出都出现，main 正常结束。成本一行代码，前提是全项目把「加锁顺序」当成一份契约来维护。

### 实验 4：数数你的机器每秒切换多少次

```bash
vmstat 1 5                    # Linux：每秒一行，共 5 行；盯 cs 列
```

预期输出（节选）：

```text
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in    cs  us sy id wa
 1  0      0 623104 148520 2234112    0    0     3     9   42  1837  8  2 90  0
 2  0      0 621900 148520 2234600    0    0     0    24  512  4120 12  3 85  0
```

判读：cs（context switch，每秒上下文切换数）动辄几千到几十万——「并行」的物理本质就是高速轮转；`us` 是用户代码时间，`sy` 是内核时间（切换本身就在其中）；`r` 列是正在等 CPU 的任务数，长期大于核数说明 CPU 在排队。Windows 等价：任务管理器 → 性能 → CPU 里有「上下文切换」计数器，Process Explorer 的 System Information 页更详细。再跑一个 CPU 密集的 Python 脚本（比如两个实验 1 的线程），对比 cs 是否明显上涨——切换频率和并发量是联动的。

## 常见坑

1. **坑 1：以为 `+=`、`dict[k] = v` 是原子操作**。现象：计数偶现偏小、字典偶现丢条目。原因：它们都是「读-改-写」复合操作，中途可被切走。排查：找共享容器/计数器的无锁写入点，用实验 1 的最小复现验证。
2. **坑 2：锁内做慢操作**。现象：多线程吞吐反而低于单线程。原因：锁里调接口、写盘，等于让所有线程排队等 IO。排查：review 锁的持有范围，把慢操作挪出临界区。
3. **坑 3：加锁顺序不一致**。现象：服务跑几小时偶现整体卡死，CPU 占用却很低。原因：两个路径以相反顺序申请同样的两把锁，概率性对峙。排查：抓线程转储（Python `faulthandler`、Java `jstack`）看谁持着谁在等谁；修复：全局固定加锁顺序。
4. **坑 4：手动 acquire 后忘记 release**。现象：锁后继无人，所有线程卡死。原因：异常一抛，release 永远执行不到。修复：一律 `with lock:`，把释放交给语言。
5. **坑 5：以为单核机器没有竞态**。现象：测试机 1 核照样跑出数据错乱。原因：切换可以发生在任意两条指令之间，单核只是「同一时刻只有一个在跑」，不是「跑完再跑下一个」。排查：竞态与核数无关，与切换点有关。
6. **坑 6：把偶现错误归咎「网络抖动」**。现象：接口偶现 500 或数据不一致，查网查了一天。原因：真正的病灶是内存里的共享状态，网络只是背锅侠。排查：先审代码里的共享可变状态，再做压测复现，最后才怀疑网络。

## 小练习

1. 把实验 1 的 `N` 改成 1000、再改成 10，各跑 10 次记录结果——解释「数据量小时竞态看起来消失」的原理，以及这对上线的危险性。
2. 复现实验 3 的死锁并修复后，把两个 `time.sleep(0.1)` 都删掉再跑 20 次——统计还能不能复现卡死，解释「竞态类 bug 时灵时不灵」与 sleep 的关系。
3. 写一个「转账」小程序：账户 A、B 各有余额 100，线程 1 反复执行「A→B 转 1 元」，线程 2 反复执行「B→A 转 1 元」，跑 10 万次后验证总额守恒——先不加锁看总额漂移，再按固定顺序加锁修复。
4. **综合排查任务**：订单服务偶现「库存少扣」，日志无异常、数据库约束也没触发。给出排查顺序：先列出代码里所有内存态的共享可变状态（计数器、缓存、标志位），逐个检查无锁复合操作；用实验 1 的最小复现思路写验证代码；最后给出修复方案并说明为什么「重启能临时缓解」却不是修复。
